# 회귀 테스트 하네스 — `zengenetics/test/`

칼륨 상세 1종을 만드는 데 **개발 6라운드 · QA 15라운드**가 걸렸다.
그 대부분은 *새로운* 결함이 아니라 **이미 통과시킨 것이 다음 라운드에 깨졌는데 아무도 다시 안 봐서* 생겼다.

- 검수 도중 파일이 바뀌어 판정서가 자기모순에 빠졌다
- 계측·SEO 통과 도장이 최종본이 아닌 이전 판에 찍혀 있었다
- 개발이 5차 전수 스캔에서 `price.css` 를 통째로 빠뜨렸다
- 2차에 제안한 수정안이 3차에 실제로 돌려보니 틀렸다

**이 하네스의 목적은 하나다 — 한 번 잡은 버그가 다시 안 나오게 하는 것.**
네 명의 QA(신아린·오세진·배시우·문가온)가 각자 판정서 안에 흩어 놓은 검사 방법을 하나로 모아 자동화했다.

---

## 돌리는 법

```bash
cd zengenetics/test

./run.sh                    # 전체 (A 보존 · B 정적 · C 실렌더 · D 계측 · E 라이브대조)
./run.sh --fast             # 정적만 (A·B). 브라우저·네트워크 안 씀
./run.sh --only C,D         # 골라서
./run.sh --refresh          # 라이브 응답을 다시 받는다 (평소엔 캐시를 쓴다)
./run.sh -v                 # PASS 항목까지 전부 출력
./run.sh --update-baseline  # 기준선 갱신 (의도적 변경 시에만)
```

끝에 PASS/FAIL 요약표가 나온다. 실패는 **어느 검사가 · 무엇이 · 기대 대비 실제**를 찍는다.
종료코드: 0 = FAIL 0건, 1 = FAIL 있음, 2 = 검사 자체가 못 돌았음.

### 소요 시간 (실측 · 2026-09-07)

| 실행 | 시간 | 무엇이 도나 |
|---|---|---|
| `./run.sh --fast` | **0.1초** | A·B (파일만 읽는다) |
| `./run.sh` | **약 1분 50초** | 위 + Chromium 21시나리오(93초) + dataLayer 5시나리오(16초) + 라이브 캐시 대조(0.2초) |
| `./run.sh --refresh` | **+약 3분** | 라이브 39응답(UA 3종 × 13페이지) + 자산 + 상세 이미지 IHDR 재수집 |

### 요약표의 세 상태

| 상태 | 뜻 | 종료코드에 영향 |
|---|---|---|
| **PASS** | 통과 | — |
| **FAIL** | 회귀. 방금 뭔가를 깨뜨렸다 | ✅ 1 로 만든다 |
| **KNOWN** | 규칙상 틀렸지만 `baseline.json` 에 **이미 알려진 결함**으로 등재된 것 | ❌ 막지 않는다 |

### Z. 제출 동결 — 항상 돈다

팀 README 「제출 동결」 규칙(*"판정 시작·종료 2회 측정해 불변임을 확인한다"*)을 자동화한 것이다.
판정 대상 7개 파일의 md5 를 **실행 시작과 끝에 각각 재고, 그 사이에 바뀌면 FAIL** 한다.
바뀌었다면 **그 실행 결과 전체가 무효**다 — *"검수 도중 파일이 바뀌어 판정서가 자기모순에 빠진"* 사고가 그것이다.

**KNOWN 은 "괜찮다"가 아니라 "이미 알고 있고 아직 안 고쳤다"는 뜻이다.**
고쳐서 0 이 되면 `--update-baseline` 으로 baseline 에서 뺀다. 그래야 다시 생겼을 때 FAIL 이 된다.

## `baseline.json`

**기대값은 코드에 하드코딩하지 않는다.** 전부 `baseline.json` 에 있다.
그리고 baseline 을 만드는 코드와 검사하는 코드는 **같은 `measure()` 함수**를 쓴다 — 둘이 갈리면 기준선이 조용히 틀려진다.

의도적으로 코드를 바꿨다면:

```bash
./run.sh --update-baseline
git commit -m "... / baseline 갱신: <무엇을 왜 바꿨는지>"
```

**커밋 메시지에 갱신 사실과 이유를 반드시 남긴다.** baseline 을 말없이 갱신하면 이 하네스는 아무것도 못 막는다.

## 거짓 통과(false pass) 방지 장치

테스트가 조용히 통과하는 것이 최악이다. 세 겹으로 막는다.

1. **`[탐지]` 검사** — 셀렉터/패턴이 **0개 매칭이면 그 자체가 FAIL**이다.
   (`C0.*.prdDetail`, `D0.nev.*`, `E3.probe.*` 등)
2. **랜드마크 선검사** — 실렌더에서 템플릿 델타(`.zg-detail`/`.zg-fold`/구성카드)가 적용됐는지 먼저 본다.
   하나라도 0이면 그 뷰포트 결과 전체를 신뢰하지 않는다.
3. **음성 대조군** — 상세 이미지 확대 검사(C3)는 **원본 폭 400px 스텁을 넣으면 확대가 "일어나야"** 통과한다(C3N).
   안 일어나면 확대 측정 자체가 죽은 것이므로 FAIL. (신아린 4차 §4 의 반례를 그대로 자동화)
4. **클릭 스텝 검증** — 계측 시나리오의 클릭 셀렉터가 하나라도 안 잡히면 FAIL(`D0.step.*`).
   아무것도 안 누른 채 "중복 없음"으로 통과하는 것을 막는다.

### A. 보존 검사 — **판매가 멈추는 종류. 가장 중요하다**

> 출처: 신아린 `QA모바일_칼륨_4차` §5 「보존 태그 24항목」 · 오세진 `QA카페24_칼륨_3차` §2-1 · 개발 `03F_개발_칼륨_6차` §2

(장바구니 버튼·옵션·가격·품절 분기). 재스킨하며 마크업을 옮기다 토큰을 흘리는 사고가 실제로 있었다.

| 검사 | 보는 것 | 실패하면 |
|---|---|---|
| `A1.*` | `module=` 39 · `{$` 231 · `onclick="{$action_` 8 · `{$form.` 17 · `id="{$` 32 · `{$total.` 7 · `@import` 28 · `displaynone` · `selectButton` · `ec-base-qty` · `{$soldout_display` · `{$basket_display` 개수 | 그 자리의 카페24 기능이 죽는다. **감소가 특히 위험** |

### C. 실렌더 검사 (Chromium)

> 출처: 신아린 `QA모바일_칼륨_4차` §1(H-1) · §2(H-2) · §4(반례) · §5(G-1/G-2·갤러리·시트·위생)

>
> 장바구니는 세션이 없어 비어 있으므로 `view_cart` 가 아니라 **`zg_cart_unreadable`** 이 난다.
> 그것이 빈 장바구니의 정상 경로이고, 그 진단 이벤트가 사라지는 것도 회귀다.

## 라이브 번들 소독 (2026-09-09) — 하네스가 자기를 속이던 것을 막은 장치

C·D 픽스처는 **라이브 HTML(캐시) + 우리 파일 주입** 이다. 2026-09-09 배포로 우리 파일
(`ds/css/detail.css` · `ds/js/detail-ui.js` · `ds/js/zg-ga4.js` · `ds/css/price.css`)이
카페24 `optimizer_user.php` **번들 안**으로 들어가면서 두 가지가 동시에 깨졌다.

| | 증상 | 결과 |
|---|---|---|
| (1) | `zg-ga4.js` 가 번들+주입으로 **2번 실행** | D 8건 FAIL (`view_item [1,2]` 등) — 라이브 결함이 아닌 하네스의 허상 |
| (2) | 주입 `<link>` 가 번들 링크보다 **앞** → 동일 특정도면 뒤에 오는 번들(=라이브본)이 이김 | **작업본이 아니라 라이브본을 검사**했다 |

(2) 의 실측(2026-09-09): 작업본 `.zg-detail .zg-fold { max-height: 1700px → 999px }` 을 넣고
`./run.sh --only C` 를 돌렸을 때 **고치기 전 하네스는 349검사 FAIL 0 — 전혀 못 잡았다.**
같은 변경에 고친 뒤 하네스는 `C4.fold` 를 FAIL 로 잡는다(기대 1700px / 실제 999px).

**지금 방식** — `checks/fixture.py` 가 자산을 서빙하기 전에 번들에서 우리 구간을 찾아

- **CSS → 그 자리를 작업본 원문으로 교체.** 잘라내고 뒤에 붙이지 않는 이유: `detail.css` 는
  라이브 번들 오프셋 **1** — 스킨 CSS 보다 앞이다. 위치를 옮기면 캐스케이드가 라이브와 달라진다.
- **JS → 그 자리를 들어냄.** 실행 주체는 주입한 `<script src="/ds/...">` **하나뿐**.
  교체가 아니라 제거인 이유 둘: ① `with_ui=False`/`with_ga4=False` 시나리오가 "그 파일을 안 올린 상태"를
  실제로 만들 수 있어야 한다. ② 예외 스택이 `/ds/js/...` 로 남아야 `errorsOurs`(우리 파일 예외만
  우리 책임) 분류가 산다 — 번들 안에서 돌면 스택이 `optimizer_user.php` 가 되어 우리 예외가
  0 으로 보이는 **거짓 통과**가 된다.

구간 찾기는 **라이브 단독본(`/ds/...` 실파일)** 과 **작업본** 두 참조본으로 각각 하고 서로 대조한다.
공백·주석을 제거한 문자열에서 ① 전체 일치, 안 되면 ② 앞 160자·뒤 160자 앵커로 범위를 잡는다.
두 참조본이 **다른 구간**을 가리키면 예외. **머리·꼬리 앵커 중 하나만 잡히면**(=번들에 있는 것 같은데
위치를 특정 못 함) **예외.** 조용히 넘어가면 지금과 똑같은 함정이 다시 생긴다.

확인 지점 — `C0.fixture.served` (우리 파일 적재 횟수: detail.css 1 · detail-ui.js 1 · zg-ga4.js 0),
`C0.fixture.price`, `C0.fixture.desanitize`. 2 가 찍히면 그 실행은 작업본을 검사한 게 아니다.

**홈(H)은 아직 주입 방식이다** — `home.css` · `home-blocks.js` · `home-hero.js` 는 라이브 번들에 없다.
들어가는 순간 상세와 똑같은 사고가 나므로 `fixture.assert_not_bundled()` 가 매 실행 확인하고,
발견하면 예외를 던진다. 그때는 그 파일들을 `fixture.BUNDLED` 로 옮겨 소독 대상으로 돌려라.

## 자동화하지 못한 것 (사람이 봐야 하는 것)

팀 README 「증명의 3단계」의 **C. 실기 확인 필요** 는 코드로 못 닫는다. 섞어서 PASS 목록에 넣지 않는다.

|---|---|---|
| 1 | `onload=` 가 카페24 저장 경로를 통과하는가 | 관리자 편집기 → 서버 저장 경로에 접근할 수 없다. 라이브에 `onload=` 전례가 0건이라 관측으로도 못 닫는다 |

| 7 | 관리자 「코드 직접입력」·스마트 주문서 디자인 | 스킨 파일 밖이라 저장소에 원문이 없다. E1 로 **결과만** 본다 |

## 새 검사를 붙일 때

1. 해당 모듈의 `measure()` 에 **관측만** 추가한다 (판정하지 않는다).

5. `./run.sh --update-baseline` → 커밋 메시지에 무엇을 왜 추가했는지 남긴다.

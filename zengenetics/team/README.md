## 작업 순서

```
① 기획 → ② 디자인 → ③ 개발 → ┬─ ④  QA(모바일)  신아린 ──REJECT──→ ③ 재작업 (최대 3회)
                              ├─ ④B QA(계측)    배시우 ──REJECT──→ ③
                              ├─ ④C QA(SEO)     문가온 ──REJECT──→ ③
                              └─ ⑤  컴플라이언스 조문규 ─┐
        QA 4종 전부 PASS → ⑥ 팀장 컨펌 → 대표님 보고 (아티팩트 갱신)
```

**검수 게이트는 3개다. 하나라도 REJECT면 팀장에게 못 올라간다.**
2026-09-06 대표님 지시로 QA 를 1명에서 3명으로 늘렸다.
2026-09-07 대표님 지시("이거 전부 카페24에서 돌아가야한다" / "검수 오래걸리면 검수인원 하나 더 늘려라")로
**QA(카페24 실환경) 오세진**을 신설해 4인 체제가 됐다.

### 카페24 무오류 원칙 (2026-09-07 대표님 지시: "검수 검수 검수 / 카페24에서 무조건 꼭 오류없이 잘 돌아가야해")

**우리는 카페24에 로그인할 수 없다.** 그래서 "돌려봤더니 되더라"가 불가능하다.
그 한계를 인정하고, **코드로 증명할 수 있는 것을 최대한 증명하고 못 하는 것은 분리해서 명시한다.**

#### 1. 설계 단계부터 검수한다 (신설)
칼륨에서 나온 반려 중 **가장 무거운 것들이 전부 "카페24 고유 동작을 몰라서"** 생겼다
(주석 안 변수 치환 / UA별 마크업 분기 / IntersectionObserver 와 `overflow:hidden` / `@js` 경로 404).
전부 **코드를 다 쓴 뒤에** 발견돼 5라운드를 돌았다.
→ **새 페이지는 코드 전에 설계서를 먼저 쓰고, 오세진(카페24 실환경)이 설계서를 먼저 검수한다.**
   플랫폼 문제를 설계 단계에서 걸러야 라운드가 줄어든다.

#### 2. 증명의 3단계 — 어디까지 증명했는지 항상 분리해서 쓴다
| 단계 | 방법 | 신뢰도 |
|---|---|---|
| **A. 라이브 실측** | `curl` 로 받은 실제 HTML·JS 번들 원문 | 가장 강함 |
| **B. 실렌더** | 라이브 HTML + 스킨 CSS 전체를 번들 순서대로 인라인 → Chromium 실제 렌더 | 강함 |
| **C. 실기 확인 필요** | 위 둘로 증명 불가 (관리자 저장 경로·iOS Safari·실주문) | **대표님 확인 항목** |

**C 를 A·B 와 섞어서 PASS 목록에 넣지 마라.** 반드시 분리해서 "대표님이 무엇을 어디서 보면 되는지" 한 줄씩 쓴다.

#### 3. 제출 동결 (오세진 제안, 2026-09-07 채택)
- 개발 제출 문서 **첫머리에 파일별 md5·바이트 표**를 붙인다.
- QA 는 **그 해시가 나오는 상태에서만 판정**한다. 판정 시작·종료 2회 측정해 불변임을 확인한다.
- **제출 후 QA 판정 전까지 대상 파일을 편집하지 않는다.** 고칠 게 생기면 다음 라운드로 넘긴다.
- 기준은 줄 수가 아니라 **바이트**. 붙여넣기 확인도 바이트 + **맨 끝 줄 문자열**.
  (실제로 검수 도중 파일이 바뀌어 판정서가 자기모순에 빠진 사고가 있었다)

#### 4. 페이지별 필수 게이트
| 페이지 | 신아린 | 배시우 | 문가온 | 오세진 | 비고 |
|---|:--:|:--:|:--:|:--:|---|
| 상품 상세 | ✅ | ✅ | ✅ | ✅ | 완료(2026-09-07) |
| **홈** | ✅ | ✅ | ✅ | ✅ | **전 트래픽 유입. 최고 위험.** 설계서 선검수 필수 |
| **브랜드 스토리** | ✅ | ✅ | ✅ | ✅ | 페이지 생성 방법부터 판정 필요 |
| 장바구니·주문서 | ✅ | ✅ | — | ✅ | 결제 경로. 배시우 필수 |

#### 5. 배포 후 확인은 검수의 일부다
코드로 못 닫은 것은 **대표님이 30초에 확인할 수 있는 형태**로 만들어 드린다.
"어디서 무엇을 보면 되는지" 한 줄. 애매한 표현 금지. 예:
> 아무 페이지 소스보기 → `fonts.googleapis` 검색 → 그 줄에 `onload=` 가 남아 있는지

### 검수 라운드 규칙 (2026-09-07 대표님 지시: "검수 3회이상씩하고 말해줘")
- **각 게이트는 최소 3회 검수한다.** 1회 PASS 로 통과시키지 않는다.
- 1차: 전수 검수 → 2차: 반려 수정분 재현 + 새 회귀 탐색 → 3차: 최종 확인(직전 라운드에서 바뀐 것만이 아니라
  **전체를 다시** 본다. 수정이 다른 곳을 밟는 일이 실제로 있었다).
- 라운드마다 판정서를 **별도 파일**로 남긴다(`_2차` `_3차`). 기존 판정서를 덮어쓰지 않는다 — 근거가 사라진다.
- 3회를 채웠어도 **REJECT 면 통과가 아니다.** 라운드는 하한이지 상한이 아니다.
- 팀장은 라운드가 길어지면 인원을 더 늘린다.
> *"절대 빠지는 거 있으면 안 돼. seo도 마찬가지고! 검수하는 인력 2배로 늘려서
> 빠짐없이 검수하고 하나씩 진행하자. 지금부터 검수팀 2배 확충한다 실시"*

확충 근거가 된 사고 2건 (둘 다 "설정은 맞았는데 결과가 틀린" 유형):
- GA4 전자상거래 이벤트가 30일간 **0건** → 매출·전환을 아무도 몰랐다
- 전 페이지 `<title>` 2개 · `canonical` 2개, 상품페이지가 홈을 canonical 로 가리킴

- 대표님 확인 방식: 아티팩트 미리보기(https://claude.ai/code/artifact/247e23e7-41dd-470a-bb36-98ac14fd27b3)를 폰으로 확인 → 번호/한줄 피드백
- 최종 판정은 항상 **대표님 폰** — SwiftShader가 못 잡는 iOS 버그가 존재함을 전 역할이 인지할 것

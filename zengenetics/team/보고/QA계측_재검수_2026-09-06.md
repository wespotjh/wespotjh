## 3. 신규 결함 — 반려 사유

### N1 🟠 `add_to_cart` / `zg_buy_click` 의 `item_variant` 가 실제 흐름에서 **항상 빈 문자열**

**파일** `ds/js/ga4.js:152-156` (`currentVariant()`), `238`, `254-257`

카페24 실JS를 붙이고 **로드 → 옵션 선택 → 장바구니 클릭** 순서를 그대로 태웠다.

```
select 상태(선택 전) : {"name":"option1","value":"*","text":"- [필수] 옵션을 선택해 주세요 -"}

zg_option_select      {"item_id":"11","item_variant":"BEST 젠제네틱스 붓기파우더 2 box (무료배송)"}   ← ✅ 정상

select 상태(선택 후) : {"value":"*","text":"- [필수] 옵션을 선택해 주세요 -"}   ← 카페24가 select 를 되돌린다
                        #totalProducts → "… - 🔥BEST🔥[지금 24%▼] 젠제네틱스 붓기파우더 2 box (무료배송) (+33,100원) 68,000원"

add_to_cart           {"value":68000,"items":[{"item_id":"11","item_variant":"", "price":68000,"quantity":1}]}
                                                                    ↑ 빈 값
```

**원인.** 카페24는 옵션을 고르면 그 옵션을 `#totalProducts` 안의 `tr.option_product` 행으로 옮기고
**`<select>` 를 `"*"`(미선택)으로 되돌린다.** `currentVariant()` 는 select 만 보므로 담기·구매 시점에는
읽을 것이 없다. 옵션을 2개 고른 경우도 동일하게 `item_variant: ""`, `quantity: 1` 이었다.

**왜 지금 드러났나 (내 1차 검수의 한계).** 1차에서는 내가 `sel.value` 를 직접 세팅하고
카페24 JS 없이 클릭했기 때문에 select 가 선택 상태로 남아 있었다. **v1부터 있던 결함이고, 이번에
카페24 실JS를 붙여서야 보였다. 1차에서 못 잡은 것은 내 책임이다.**

**왜 REJECT인가.** 차터 검수방법 3: *"이벤트별로 파라미터 값까지 대조한다. **이벤트 이름만 맞고
값이 비면 REJECT**."* 그리고 추적계획 §3 은 *"몇 박스가 팔리는지는 `item_variant` 로 잡는다"* 로
이 파라미터를 핵심 지표로 지정했다. R5 를 고친 목적 자체가 여기다 — 정리 규칙은 완벽해졌는데
**정작 담기·구매 이벤트에는 실리지 않는다.**
(`zg_option_select` 에는 정상적으로 실리므로 박스 수량 자체는 측정 가능하다. 그래서 🔴 가 아니라 🟠 다.)

**수정 지시.** select 가 비어 있으면 카페24가 옮겨 놓은 선택 결과에서 읽는다.
실측한 DOM은 아래와 같다(라이브 실JS 구동 결과, 옵션 2종 선택 상태).

```html
<tr class="option_product " data-option-index="1" target-key="11">
  <td><input type="hidden" class="option_box_id" …>
      <p class="product">젠제네틱스 포타슘 칼륨 (20ea)<br> - <span>[지금 22%▼] 젠제네틱스 붓기파우더 1 box</span></p></td>
  <td><span class="quantity"><input type="text" name="quantity_opt[]" class="quantity_opt" value="1" product-no="11"> …
</tr>
```

```js
  function selectedOptionRows() {
    var rows = document.querySelectorAll('tr.option_product');
    var out = [];
    Array.prototype.forEach.call(rows, function (r) {
      var sp = r.querySelector('p.product span');
      var qi = r.querySelector('input.quantity_opt, input[name^="quantity_opt"]');
      var q  = qi ? n(qi.value) : 1; if (q <= 0) q = 1;
      if (sp) out.push({ variant: cleanVariant(txt(sp)), qty: q });
    });
    return out;
  }
  function currentVariant() {
    var sel = document.querySelector('select[name^="option"]:not([name^="addproduct"])');
    if (sel && sel.value && sel.value !== '*' && sel.value !== '**') {
      return cleanVariant((sel.options[sel.selectedIndex] || {}).text || '');
    }
    var rows = selectedOptionRows();              /* 카페24가 select 를 되돌린 뒤 */
    return rows.length ? rows.map(function (r) { return r.variant; }).join(' + ') : '';
  }
```
`quantity` 도 같이 살리는 것을 권한다 — `items[0].quantity` 를 `Σ selectedOptionRows().qty` 로 두면
현재 항상 `1` 로 고정된 수량이 실제값이 되고, 단가 역산(R8)도 더 정확해진다.

**검증 요구**: 미러 하네스(`rt_variant.mjs`)에서 옵션 선택 후 `#actionCart` 클릭 →
`add_to_cart.items[0].item_variant` 에 `2 box` 가 포함되고 `%` 는 없을 것.

### N2 🟠 `begin_checkout` — 5초 폴링 중 이탈하면 **이벤트가 통째로 유실**

**파일** `ds/js/ga4.js:373-389`

팀장 지시 (3) 4가지를 각각 실측했다. **라이브 주문서 원문**(265KB, 스크립트만 제거)에 발사 시각을 찍었다.

| 케이스 | 결과 | 판정 |
|---|---|---|
| 값이 안 채워짐 | `+5030ms` `begin_checkout {checkout_route}` + `zg_checkout_value_unreadable {has_paybox:1,has_paybtn:1}` | ✅ 틀린 값 대신 미발사 |
| **배송비 3,000원만** (`.totalPrice`에 `<strong>` 주입) | `+5031ms` **value 없음** | ✅ 옛 버그 소멸 |
| 최종 결제 금액 즉시 채움 | `+8ms` `{"value":110900}` | ✅ |
| 값이 **2초 뒤** 채워짐 | `+2018ms` `{"value":110900}` | ✅ 폴링 동작 |
| `.totalPay` 제거 + 결제버튼 span | `+7ms` `{"value":110900}` | ✅ 폴백 ③ |
| **12초 방치** | `begin_checkout` **정확히 1건** | ✅ **중복 없음** |
| 적용금액 55,555 / 적립 1,109 / 결제금액 77,777 만 채움 | `+5025ms` **value 없음** | ✅ 엉뚱한 블록을 안 집는다 |
| **2.5초 시점 이탈** | **이벤트 0건** | ❌ **유실** |
| 장바구니 빈 DOM | `+8ms` `zg_cart_unreadable` | ✅ 폴링이 지연시키지 않음 |
| 주문완료 빈 DOM | `+33ms` `zg_purchase_unreadable` | ✅ 폴링이 지연시키지 않음 |

**문제.** 값을 못 읽는 동안 `begin_checkout` 자체를 붙잡고 있다. 값이 끝내 안 채워지면 **5초** 뒤에야 나가고,
그 전에 뒤로가기·창닫기로 나가면 **아무것도 안 나간다.**
유실은 무작위가 아니라 **빨리 이탈한 사람 쪽으로 편향**된다 → `begin_checkout` 이 분모인
`주문서 → 결제완료` 전환율(기준선 52.4%)이 **실제보다 높게** 나온다. 틀린 숫자를 만드는 것과 같다.

**수정 지시.** 도달과 금액을 분리한다.

```js
  if (/\/order\/orderform\.html/i.test(path)) {
    var v0 = checkoutTotal();
    if (v0) { send('begin_checkout', { currency:'KRW', value:v0, checkout_route:'orderform' }); }
    else {
      send('begin_checkout', { checkout_route:'orderform' });          /* ① 도달은 즉시 기록 */
      var ckTries = 0;
      (function tick(){                                                /* ② 금액은 따로 뒤따라 보낸다 */
        var v = checkoutTotal();
        if (v) { sendAlways('zg_checkout_value', { currency:'KRW', value:v, checkout_route:'orderform' }); return; }
        if (ckTries++ >= 25) { sendAlways('zg_checkout_value_unreadable', {…}); return; }
        setTimeout(tick, 200);
      })();
    }
  }
```
`begin_checkout` 은 **항상 즉시** 나가므로 퍼널 분모가 온전해지고, 금액은 `zg_checkout_value` 로 따라온다.
(대안: `visibilitychange`/`pagehide` 에서 폴링을 강제 종료하며 flush. 어느 쪽이든 "도달 즉시 기록"이 조건이다.)

### N3 ⚠️ `purchase` 는 폴링이 없다 — 주문서와 비대칭

`begin_checkout` 은 값이 늦게 채워지는 것을 전제로 5초 폴링하는데, **`purchase` 는 `DOMContentLoaded`
시점에 한 번만 읽는다.** 라이브 주문완료가 서버 렌더라면 문제없지만(마크업상 그렇게 보인다 —
주문번호 자리가 `<span class="txtEm"></span>` 로 JS 훅이 없다), **만약 주문서처럼 JS로 채우는 구조라면
모든 주문이 `zg_purchase_unreadable` 로 빠진다.** 매출이 통째로 0이 되는 실패다.

실측으로도 재현했다 — 값을 ga4.js **부팅 후**에 채우면:
```json
{"event":"zg_purchase_unreadable","has_order_id":0,"has_value":0,"item_count":0}
```
부팅 **전**에 채우면 정상:
```json
{"event":"purchase","transaction_id":"20260906-0007777","value":110900,"item_count":1,"shipping":3000,
 "items":[{"item_id":"11","item_variant":"붓기파우더 2 box (무료배송)","quantity":1,"price":107900}]}
```

**지시.** 실주문 1건으로 DebugView 확인 후, `zg_purchase_unreadable` 이 뜨면 `begin_checkout` 과
같은 폴링을 `purchase` 에도 넣을 것. (지금 코드를 바꾸라는 뜻이 아니라 **확인 절차를 반드시 밟으라**는 뜻이다 — §6 L4)

### N4 🟢 스니펫에 `try/catch` 가 없다

`gtag` 가 어떤 이유로든 할당·호출 불가 상태면 스니펫이 **결제 페이지 `<head>` 에서 예외를 던진다**
(재현: `window.gtag` 를 읽기전용으로 만든 상태 → `TypeError: window.gtag is not a function`).
가능성은 낮지만 대표님이 직접 붙여넣는 코드이고 대상이 결제 페이지다. 한 줄이면 막는다.

```html
<script>try{(function(){window.dataLayer=window.dataLayer||[];if(typeof window.gtag!=='function'){window.gtag=function(){window.dataLayer.push(arguments);};window.gtag('js',new Date());}window.gtag('config','G-GZHFY596SS');})();}catch(e){}</script>
```

### N5 🟢 옵션세트 주문의 `purchase.item_variant` 공백

라이브 주문완료 마크업에는 옵션이 들어갈 자리가 **두 군데**다.
```html
<li title="옵션">
  <p class="option displaynone"></p>                                  ← 코드가 읽는 곳
  <ul class="xans-element- xans-order xans-order-optionset option">   ← 세트 주문은 여기에 실린다
    <li><strong>{$product_name}</strong>{$option_str} ({$qty}개)</li>
  </ul>
</li>
```
`ul` 쪽에만 값이 있는 상태를 만들어 돌린 결과 `item_variant: ""` 였다(값 오류는 아니고 누락).
`p.option` 이 비면 `ul.xans-order-optionset` 을 읽는 폴백을 권한다.

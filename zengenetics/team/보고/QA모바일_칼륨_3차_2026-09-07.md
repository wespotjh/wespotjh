## 2. 개발이 내 지시를 바꾼 2건 — 판정

### 판정 ①. G-1 의 상수 `8px` 제거 → **옳다. 내 지시보다 낫다.**

내가 준 `8px` 은 **바 92px 전제**에서 나온 값이다. 같은 라운드에서 G-2 가 바를 82px 로 바꿨으므로
그 상수를 그대로 쓰는 것은 틀린다. 개발은 **G-2 후 재측정해서 다시 유도**했고, 그게 정확한 절차다.

```
바 높이 = 82 + sa      (실측 확정)
예약    = 100(스킨 !important) + P
여유    = 100 + P − (82 + sa) = 18 + P − sa
→ P = sa  ⇒  여유 = 18px (safe-area 와 무관하게 일정)
```

내 실측이 이 유도를 뒷받침한다 — **전 폭·양쪽 safe-area 에서 +17.6~18.4px 로 일정**하다.
부수 이득도 맞다: `max()`/`calc()` 가 빠져 **`env()` 만 쓰므로 iOS 11.3+ 호환**이고(내 2차 안보다 넓다),
비노치에서는 `env()` = 0 이라 **현재와 완전히 동일**하다. `@media (max-width:1023px)` 스코프도 확인했다(1024/1280 에서 `body padding-bottom: 0px`).

### 판정 ②. G-4 의 `min-width` 우회 — **방향은 옳으나 상수가 틀렸다. §3 참조.**

"폭이 `!important` 로 잠겨 있으니 `min-width` 로 우회한다"는 **접근 자체는 옳다**(내가 제시한 `width`/`height` 속성 방식은
실제로 돌려 보니 **스크롤 전 요청 14장**으로 lazy 가 무력화된다 — §5 표 B안. 내 예상이 틀렸고 개발 방식이 맞다).
문제는 `100%` 라는 값의 **전제**다.

**결과 — 실렌더 대조 (원본과 같은 640px 폭 스텁을 서빙):**

| 뷰포트 | 우리 CSS **ON** | **OFF** | 확대 |
|---|---|---|---|
| 320 / 390 / 414 / 640 | 320 / 390 / 414 / 640px | 동일 | 없음 ✅ |
| **768** | **768px** | 640px | **+20% ❌** |
| **900** | **868px** | 640px | **+36% ❌** |
| **1023** | **991px** | 640px | **+55% ❌** |
| 1024 / 1280 | 640px | 640px | 없음 ✅ |

- 641~1023px 구간은 **아이패드 세로(768/820/834)·갤럭시탭·큰 폰 가로(932)·좁은 데스크톱 창**이 전부 들어간다.
- 이 구간에서 **상세 이미지 14~25장 전부**(= 판매 카피 전량)가 흐려진다. 레이아웃은 안 깨지지만 **화질 회귀**다.
- **우리 CSS 를 끄면 640px 원본 크기로 정상 렌더된다** → 명백히 이번 라운드가 만든 회귀다.
- 대표님 폰(390px)에서는 **드러나지 않는다.** 실기 검수로 잡히지 않는 종류다.

**수정 지시 (실렌더 검증 완료 — §5 A안)**
```css
@media (max-width: 1023px) {
  /* 원본 폭 실측 639~640px (라이브 6개 상품 101장, PNG IHDR 확인).
     100% 로 두면 641~1023px 에서 최대 +55% 확대된다. 상한을 원본 폭으로 잠근다. */
  .zg-detail #prdDetail .zg-fold img { min-width: min(100%, 640px); }
}
```
- 검증 결과: 390px 확대 없음 · **768/1023px 확대 1.00x** · 스크롤 전 요청 **2~3장** · 최종 **14/14 로드** · 로드 전 자리 **14/14 분산**.
- 8종 전개 시에도 안전 방향이다 — 640px 보다 **넓은** 원본이 와도 `min(100%, 640px)` 은 확대하지 않는다.
  640px 보다 **좁은** 원본이 오면 그 상품만 로드 전 자리 예약이 실제보다 커지는데, **화질에는 영향이 없다**(레이아웃 예약값일 뿐).
- 아울러 `aspect-ratio: auto 1080 / 1600` 의 `1080/1600` 도 원본과 무관한 값이다.
  `auto` 키워드 덕분에 **로드 후에는 자연 비율이 이겨 왜곡이 없으므로 기능상 무해**하지만,
  로드 전 예약 높이가 실제와 달라 스크롤 점프를 키운다. `640 / 948`(실측 중앙값)로 맞추면 더 정확하다. **권고 사항.**

### P0-2 【H-2】 클립한 `select` 가 문서를 **35px 가로로 넘긴다**

```
우리 CSS+JS ON   scrollWidth = 425 , clientWidth = 390   ❌ 가로 스크롤 발생
우리 CSS OFF     scrollWidth = 390 , clientWidth = 390   ✅
넘치는 요소      SELECT.ProductOption0.zg-a11y-hide   right=425  width=390
```

**원인:** `.zg-a11y-hide { width:1px; height:1px }` 는 **(0,2,0)** 인데,
같은 파일의 `.zg-detail .xans-product-detail .infoArea .productOption select { width:100%; height:44px }` 이 **(0,4,1)** 로 이긴다.
→ 클립된 select 의 **레이아웃 박스가 390px 그대로 남는다.**
`clip-path: inset(50%)` 는 **페인팅만** 자르고 박스는 남기므로, 절대배치된 390px 박스가 문서 우측으로 삐져나온다.

- 증상: 상품 상세 페이지 전체가 **좌우로 35px 흔들린다**(모바일에서 눈에 띄는 결함).
- 개발도 §9 에서 `scrollWidth 425 > clientWidth 390` 을 관측했으나 *"우리 CSS 유무 무관하게 동일"* 로 결론냈다.
  **내 대조 결과는 반대다** — 우리 시트를 끄면 390 이 된다. (개발 하네스가 시트 토글 대조를 안 한 것으로 보인다.)

**수정 지시 (실렌더 검증 완료)**
```css
/* 클립 유틸이 select 스타일 규칙(0,4,1)에 지지 않도록 구체도를 맞춘다.
   clip-path 는 페인팅만 자르므로 박스 자체를 1px 로 만들어야 가로 넘침이 없다. */
.zg-detail .xans-product-detail .infoArea .productOption select.zg-a11y-hide {
  width: 1px; height: 1px; min-width: 0;
}
```
- 검증: `scrollWidth 390` ✅ · select 박스 22px(뷰포트 안) · **`display`·`visibility` 정상이라 카페24 검증 포커스 경로 유지** ✅

**판정: 우려는 실현되지 않는다. 모호성 0. 코드 수정 불필요.**

## 10. 개발에게 — 이번 라운드 평가

- **G-1~G-4 를 전부 고쳤고, 전부 실렌더 수치로 증명했다.** 검수 방법까지 내 방식으로 맞춰 온 것이 이번 라운드의 가장 큰 진전이다.
  이제 우리 둘이 **같은 자로 잰다.** 수정 전 값을 자기 하네스에서 −26.1px / 92px / 12×12 로 **재현한 뒤** 고친 절차도 옳다.
- **내 지시의 상수 `8px` 을 그대로 받지 않고 재유도한 것이 맞다.** 내 상수는 92px 전제였고 G-2 가 그 전제를 바꿨다.
  `P = sa` 유도는 상수를 없애고 호환 범위까지 넓혔다. **QA 지시도 검증 대상이라는 태도가 옳다.**
- 내가 2차에 제안한 `width`/`height` 속성 방식(B안)은 **실제로 돌려 보니 lazy 를 무력화한다.** 개발의 `min-width` 접근이 맞았다.
- 「시트 열림 시 리뷰 버튼 2px」은 **실렌더가 아니면 못 찾는 결함**이었고, 지시받지 않은 것을 스스로 찾아 고쳤다.
- 오세진 6건까지 같은 라운드에 처리했고, `zg-ga4.js` 는 **개명만·md5 불변**으로 승인 대기 항목을 정확히 지켰다.

다만 **H-1 은 "원본 폭 1080px" 이라는 검증되지 않은 전제 위에 세워졌고, 그 전제가 틀렸다.**
개발 스스로 §9 에서 *"8종 복제 전 원본 폭을 확인해 달라"* 고 올렸는데 — **확인해 보니 11번부터 이미 640px 이었다.**
불안한 지점을 정확히 지목한 것은 맞다. 다음 라운드에는 **전제부터 재고 시작하자.**

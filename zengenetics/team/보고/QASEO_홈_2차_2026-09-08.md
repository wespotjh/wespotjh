### P1-B `preload` — ✅ 반영 (위치 판단 포함)

**"`@css` 앞인가" 에 대한 답:** `:21 @css` 는 카페24가 `<head>` 번들로 **끌어올리는 디렉티브**라 그 줄에서 아무것도 출력되지 않는다. 따라서 파일 내 `@css` 와의 상대 위치는 무의미하고, 실제 문서에서는 head CSS 번들 → body 파싱 → `:63` 순이다. 인라인 `<style>`(`:64`) **바로 앞**이라 CSS 규칙보다 먼저 요청이 시작된다 — 의도 충족. (파일 최상단 `:2` 로 올리면 매니페스트 2.4KB 만큼 더 앞당겨지나 체감 차이 없음 — P3)

**preload 404(미리보기 `/ds/` 해석) 부작용:** 콘솔 경고 1건 + 요청 1회 낭비뿐. 렌더·색인·접근성 영향 **0** — 같은 환경에서 `.zg-bg0` 배경 자체도 404 라 preload 가 새로 만드는 결손은 없다. 실기·적용 스킨에서는 200.

### P1-E 카운터 최종값 — ⚠ **마크업 반영 ✅ / JS 잔여 1줄 (3차 필수)**

`index.html` `:188-229` → `525/20 · 400/20 · 4/20` ✅. **서버 응답·JS 꺼짐 상태의 DOM 은 「칼륨 525 mg」이다.**

그러나 `home-blocks.js`(불변) `:147-148` 은 조건 없이 `v0.textContent = Math.round(n0 * e)` 를 쓴다. `renderBlock` 은 `:126` 에서 **블록 상단이 2뷰포트 안**이면 실행되고, 그때 p<0.62 → e=0 → **텍스트가 다시 `0` 이 된다.**
- 일반 사용자: 밴드 `opacity:0` 구간이라 안 보임 → 문제 없음.
- **Googlebot 렌더:** 뷰포트를 세로로 길게 잡아 지연 콘텐츠를 깨우는 방식이라 `r.top > vh*2` 가드가 열릴 수 있다 → 렌더 후 DOM 이 `0 mg` 으로 되돌아갈 여지가 있다. 개발 보고 "크롤러가 보는 DOM 은 525" 는 **`renderBlock` 이 그 블록에 대해 실행되지 않을 때만** 참이다.

**내 1차 명세("마크업에 최종값, JS 가 0부터 센다")가 이 경우를 빠뜨렸다 — 개발은 명세대로 했다.** 그래서 REJECT 전환 대상이 아니다.

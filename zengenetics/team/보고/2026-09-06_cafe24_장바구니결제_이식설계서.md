## A. 현재 공홈 동선 지도

```
[상품상세]  /product/detail.html?product_no=11
   │  옵션 select(name=option1) 선택 → "장바구니" 클릭
   │  onclick="product_submit(2, '/exec/front/order/basket/', this)"
   ▼
[담기 API]  POST /exec/front/order/basket/     (AJAX, async:false, dataType json)
   │  응답 {result, alertMSG, …}
   │  · sType=2(장바구니) → 레이어 띄우고 머무름
   │  · sType=1(바로구매) → 아래 주문서로 이동
   ▼
[장바구니]  /order/basket.html            (해외배송 탭은 ?delvtype=B)
   │  수량변경  POST /exec/front/order/basket/   command=update
   │  선택삭제  POST /exec/front/order/basket/   command=select_delete
   │  주문      POST /exec/front/order/order/    {checked_product, basket_type, delvtype, ch_ref}
   │            응답 {result, isLogin, alertMSG}
   ├── isLogin=='F' →  /member/login.html?noMember=1&returnUrl=<주문서URL>&checked_product=…
   │                     └ 이 화면에서만 "비회원 구매" 버튼이 노출된다
   ▼
[주문서]    /order/orderform.html?basket_type=all_buy[&delvtype=][&paymethod=][&only_one_paymethod=T]
   │  ※ cafe24 "원터치 주문서" — 스킨상 읽기 전용 파일
   ▼
[주문완료]  /order/order_result.html
```

### A-1. 각 단계 상세

**① 상품상세 → 담기**
- URL: `/product/detail.html?product_no={no}` (SEO 별칭 `/product/{슬러그}/{no}/` 도 유효 — `[확인됨]` `link_product_detail = '/product/젠제네틱스-포타슘-칼륨-20ea/11/'`)
- **상품상세 HTML 안에 `<form>` 태그가 없다.** `[확인됨]` — detail11.html 전체에서 `<form>` 은 검색바(`#searchBarForm`) 2개와 빈 `#frm_image_zoom` 4개, 총 6개뿐이다. cafe24는 담기 시점에 **`#frm_image_zoom` 을 전송폼으로 재활용**해 hidden 필드를 JS로 채워 넣는다. `[확인됨]` `PRODUCTSUBMIT.oConfig = {'sFormSelector': '#frm_image_zoom'}`.

### B-4. 품목 필드 (`setSelectedItem()`) — **가장 중요** `[확인됨]`

> 각 항목 끝의 대괄호가 근거 등급이다. 심의 관련 항목은 대표님 지시에 따라 **작성하지 않는다.**

**E-1. 상품상세에 전송용 `<form>` 이 없다 — cafe24 JS 없이는 담기가 성립하지 않는다.**
`[확인됨: detail11.html 전체의 <form> 은 6개뿐 — 검색바 2 + 빈 #frm_image_zoom 4. 상품 전송용 폼은 0개]` + `[확인됨: PRODUCTSUBMIT.oConfig.sFormSelector='#frm_image_zoom']`
→ 우리 페이지를 그대로 얹고 "버튼만 연결"하는 방식은 성립하지 않는다. **cafe24 프런트 번들(`/ind-script/optimizer.php`)과 상품상세 컨텍스트 변수(`iProductNo`, `product_price`, `has_option`, `basket_type` 등)가 같은 문서 안에 있어야 한다.** → C-0 A안이 필요한 이유.

**E-2. 주문서는 우리가 디자인할 수 없다 (원터치 주문서, 읽기 전용).**
`[확인됨: orderform.html 스킨 주석 "이 파일은 원터치 주문서의 읽기 전용 파일입니다 … 자동으로 개선된 소스가 적용되어"]`
→ 주문/결제 화면 디자인은 **관리자에서 제공하는 범위(색·타이포·영역 노출)까지만**. 우리 톤앤매너를 100% 적용할 수 없다. **대표님 눈높이 조정이 필요한 지점.**

**E-3. 우리 상품페이지의 '같이 담기'가 cafe24 추가구성상품과 어긋난다.**
`[확인됨]` 공홈 11번 상세의 추가구성상품 = **63(붓기부스터 SET) · 13(비타민B) · 16(마그네슘)**.
우리 `product-potassium.html:315~320` 의 '같이 담기' = 마그네슘 · 비타민B · **마그네슘 데이팩 · 비타민B 데이팩**.
→ 데이팩(61·62)은 **상품으로는 존재하지만 11번의 추가구성상품으로 등록돼 있지 않다.** 둘 중 하나를 골라야 한다: ①cafe24 관리자에서 61·62를 추가구성상품으로 등록 ②우리 페이지에서 데이팩을 뺀다. **대표님 결정 필요.**

**E-4. 비어 있는 장바구니로 주문서에 들어가면 홈으로 튕긴다.**
`[확인됨: orderform.html 첫머리 alert('주문서로 이동할 수 없습니다.');location.replace('/')]`
→ 우리 "구매하기"가 담기 성공을 확인하지 않고 주문서로 보내면 사용자는 **알림창 + 홈 이동**을 맞는다. 담기 응답 `result >= 0` 을 반드시 확인한 뒤 이동할 것.

**E-5. 우리 페이지가 금액을 자체 계산한다 — 주문서 금액과 어긋날 수 있다.**
`[확인됨: product-*.html:373~402 calc() 가 상품금액·할인·배송비·총액을 프런트에서 직접 산출]`
지금 값(정가 45,000/49,000, 배송비 3,500, 무료기준 50,000, 박스별 가격)은 **공홈과 대조해 전부 일치**함을 확인했다. 그러나 쿠폰·적립금·회원등급 할인·다중배송비는 우리 계산에 없다.
→ 표시 문구를 "결제 예상 금액"으로 유지하고(현재 그렇게 되어 있음 — 적절), 최종 금액은 cafe24 주문서가 정한다는 점을 유지한다. 장기적으로는 계산 자체를 cafe24(`/exec/front/order/calculator`)에 넘긴다.

**E-6. "두 박스부터 무조건 무료배송" 이라는 우리 문구의 근거가 cafe24에 없다.**
`[확인됨]` cafe24 배송비 정책은 **금액 기준 하나뿐**(3,500원 / 50,000원 이상 무료). 옵션명에 붙은 "(무료배송)" 은 표시 텍스트다.
`[확인됨]` 실무상 결과는 같다 — 2박스 가격이 칼륨 68,000 / 비타민B·마그네슘 72,000 으로 모두 50,000을 넘기 때문.
`[추정]` 옵션 단위 무료배송 규칙은 존재하지 않는다.
→ 문구 자체는 결과적으로 참이라 급하지 않으나, **가격이 내려가면 즉시 거짓이 되는 구조**다. "5만원 이상 무료" 기준으로 통일하는 편이 안전. `product-potassium.html:218` / `:391` / `:399`.

**E-7. 페이지 1개가 1.6MB 인라인 data-URI다 — 스킨에 그대로 못 넣는다.**
`[확인됨: product-potassium.html 290행 한 줄이 1,624,139자]`
→ cafe24 스킨 파일 용량·편집기 한계, 그리고 상세이미지는 cafe24 상품 상세이미지로 관리되어야 한다. **이미지 분리 작업이 이식의 선행 조건.**

**E-8. 인라인 편집 모드(`zg-edit-mode`)는 cafe24에서 동작하지 않는다.**
`[확인됨: product-*.html:431~ 이 `claude.use('artifact')` 에 의존]`
→ 대표님의 "텍스트·자간 직접 수정" 요구를 cafe24 이식본에서 어떻게 이어갈지 별도 답이 필요하다. **대표님 결정 필요** (WORKLOG B-2의 피그마 안건과 같은 줄기).

**E-9. 사이트 검색에서 '데이팩'이 안 잡힌다.**
`[확인됨: /product/search.html?keyword=데이팩 → "검색결과가 없습니다"]` / `[확인됨: /product/list.html?cate_no=54 에는 60·61·62 정상 존재]`
→ 상품 부재가 아니라 검색 색인/제외어 설정 문제. 광고·상세페이지에서 데이팩으로 유입된 사용자가 검색으로는 못 찾는다. **cafe24 관리자에서 확인 필요.**

**E-10. 결제수단 실목록을 확인하지 못했다.**
`[확인 불가]` — 주문서 결제수단 영역은 장바구니가 차 있어야 렌더된다.
`[확인됨]` 정적으로 준비된 것: 결제위젯 · 카드사 직접결제 · 무통장입금 · 현금영수증. 카카오페이 바로결제 링크와 네이버페이 체크아웃 SDK도 로드된다.
→ B-9 검증 때 함께 캡처할 것.

**E-11. 담기 요청의 세션/보안 요구사항 미검증.**
`[추정]` 쿠키 세션만 있으면 될 것이다. `[확인 불가]` CSRF 토큰·Referer 검사·Origin 제한 여부.
→ **B안(우리가 직접 POST)을 택할 경우 가장 큰 미지수.** A안이면 이 리스크가 사라진다.

**E-12. 소셜로그인이 카카오 하나뿐이다.**
`[확인됨]` 네이버·구글·애플·페북·LINE 버튼은 모두 `displaynone`, `onclick` 비어 있음.
→ 우리 로그인 화면 디자인에 5종 버튼을 그려두면 안 된다. **카카오 1개 기준으로 설계.**

**E-13. 장바구니 행(row) 마크업을 못 봤다.**
`[확인 불가]` — 비로그인·빈 장바구니라서. 수량변경/삭제/선택주문 **동작 규격(엔드포인트·파라미터)** 은 JS에서 전부 확보했으나(A-1 ②·B-8), **DOM 구조는 미확인**이다.
→ 장바구니 화면을 우리 디자인으로 바꾸려면 이 부분을 먼저 캡처해야 한다.

**E-14. 해외배송 장바구니가 별도로 존재한다.**
`[확인됨]` `/order/basket.html?delvtype=B`, "해외배송 상품과 국내배송 상품은 함께 결제하실 수 없으니 장바구니 별로 따로 결제해 주시기 바랍니다."
→ 우리 화면이 장바구니를 하나로만 그리면 해외배송 이용자가 자기 상품을 잃어버린 것처럼 느낀다. 국내(A)/해외(B) 탭을 유지할 것.

**E-15. 옵션 미선택 상태가 기본이다.**
`[확인됨]` 세 상품 모두 첫 옵션이 `- [필수] 옵션을 선택해 주세요 -` 이고 `required="true"`.
반면 우리 페이지는 **2박스가 미리 선택된 상태**(`var sel=2`)로 시작한다.
→ 이식 시 우리 UI의 "미리 선택" 을 유지하려면, 담기 전에 cafe24 select 값을 프로그램적으로 세팅해줘야 한다. 안 하면 "옵션을 선택해 주세요" 로 막힌다.

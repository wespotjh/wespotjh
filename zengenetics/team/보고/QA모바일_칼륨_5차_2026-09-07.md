## 5. AC 105개 — **구현 105 / 미구현 0 / 오구현 0 (유지)**

이번 변경이 건드린 AC 는 **K-04 AC3** 하나다.

> AC3: *“카드에 표시하는 텍스트는 option 의 `text` 를 그대로 쓴다. … 표시 정리는 **문자열 가공까지만** 허용:
> 대괄호 태그(`[지금 24%▼]`)·이모지를 앞줄 뱃지로, 나머지를 본문으로 분리. **숫자는 손대지 않는다.**”*

| 요건 | 판정 |
|---|---|
| option `text` 를 그대로 쓰는가 (문구 창작 없음) | ✅ 13종 전수 확인 — 원문에 없는 글자가 카드에 나온 사례 0 |
| 숫자를 손대지 않는가 | ✅ 할인율·기간·추가금 전부 원문 그대로 |
| 문자열 가공까지만 하는가 | ✅ 분해·재배치뿐, 계산 없음 |
| 대괄호를 앞줄 뱃지로 | **조건부** — 비-BEST 는 뱃지(칩). **본문이 비는 B형 BEST 3장만 제목으로 승격** |

**→ 구현으로 센다.** 근거: AC3 의 규범적 핵심은 “창작 금지·숫자 불변·가공까지만”이고 셋 다 충족한다.
대괄호 배치 문언을 문자 그대로 적용하면 **B형 BEST 3장은 제목이 없어야 한다** — 그것이 방금 고친 P0 이다.
**문언이 B형 데이터 형태를 상정하지 않았을 뿐, 코드가 AC 와 충돌하지는 않는다.**

> **K-04 AC11 과 다르게 판정한 이유를 밝힌다.** AC11 은 `aria-pressed` 가 **확정 동작(여러 구성 담기)과 정면 충돌**하는
> **모순**이었기에 오구현으로 셌다. 이번은 **문언이 다루지 않은 공백(gap)** 이다. 성격이 다르므로 다르게 센다.
> 다만 **기획 문안 보완은 권고한다** — AC11 때와 같은 방식으로 한 문장 추가하면 된다:
> *“대괄호를 걷어내면 본문이 비는 옵션(세트 상품)에서는 대괄호를 제목으로 쓴다.”*
> 기획이 “대괄호는 반드시 뱃지”로 확정하면 그때 오구현으로 재분류한다.

## 6. 운영 규칙 7번 평가 (요청하신 것)

> 신설 규칙: *“조사서 문구를 조건으로 옮길 때 걸리는 나머지 전부를 세어 볼 것”*

**옳은 교훈이다. 다만 절반이다.** 완성형으로 바꿀 것을 제안한다.

- 이번 사고의 형태는 **“3종만 해당”이라는 조사서 문장을 판별식으로 옮겼더니 6종이 걸린 것”** 이다.
  규칙대로 “걸리는 나머지”를 셌기 때문에 개발이 **제출 전에 스스로 잡았다.** 규칙이 실제로 작동했다.
- 그런데 이것은 **이번 프로젝트에서 세 번째로 같은 형태의 사고**다.
  | 라운드 | 사고 | 공통 형태 |
  |---|---|---|
  | 2차 H-2 전신 | “가로 넘침은 우리 CSS 무관” | **대조군 없이** 한 조건만 보고 결론 |
  | 3차 H-1 | “원본 폭 1080px” | **전수 확인 없이** 대표 사례(프로토타입)로 결론 |
  | 5차 F-3 | “가격 없는 상품 3종” | **반대편 집합을 세지 않고** 조건으로 이관 |
  셋 다 **“집합을 세지 않고 대표 사례로 결론”** 이다.
- **그래서 규칙을 이렇게 쓰기를 제안한다:**
  > **판별식을 만들면 전수 집합에 돌려 참·거짓 **양쪽 개수**를 세고, 조사서가 말한 기대 집합과 대조한다.
  > 수가 다르면 조사서가 틀렸거나 판별식이 틀린 것이다 — 어느 쪽인지 밝히기 전에는 제출하지 않는다.**
  “걸리는 나머지”만 세면 **거짓 음성**(걸려야 하는데 안 걸리는 것)을 못 잡는다.
  이번엔 `hasRealPrice()` 가 60·61·62 를 **거짓으로 만든** 사고였으니 정확히 그 반대편이었다.
- **13종 전수 프로빙(1~120 `curl`)이 이 규칙의 도구다.** 조사서에서 가장 값진 산출물이고,
  앞으로 판별식이 들어갈 때마다 그 목록에 돌리면 된다. 나도 이번 판정에 그대로 썼다.

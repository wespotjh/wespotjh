## 1. ★ 1차 판정서 근거 정정 2건 — 내 잘못이 맞다

### 정정 1. R2 의 푸터 예약값 — **개발 보고가 옳다**

내가 인용한 것은 `css/module/product/detail.css:1` `html .footer{padding-bottom:60px}` 뿐이었다.
같은 파일 **4248행**(`@media (max-width:1023px)` 블록 3606~4330 안)에

```css
.footer { padding-bottom: 100px !important; }
```

가 따로 있다. **모바일 예약은 60px 이 아니라 100px 이다.** 실렌더 computed style 로도 `padding-bottom: 100px` 확인.
→ 1차 R2 의 "예약은 60px 뿐" 문장을 철회한다. 다만 **결론(바가 푸터를 가린다)은 그대로 유효하다** — §2 참조.

### 정정 2. R5 의 부속 근거 — **1차 개발 주석이 JS 에 한해 옳았다**

1차에 나는 *"`optimizer_user.php` 는 `<head>` 안이다(119,937 byte)"* 라고 썼다.
그 위치는 **CSS 번들**(`<link rel="stylesheet" … type=css>`)이었고, **JS 번들은 `</body>` 근처**다:

| 번들 | 라이브 HTML 내 위치 | `</head>`=121,031 / `</body>`=328,763 |
|---|---|---|
| optimizer.php **(css)** | 119,512 | head |
| optimizer_user.php **(css)** | 119,880 | head |
| optimizer.php **(js)** | **289,446** | **body 끝** |
| optimizer_user.php **(js)** | **291,346** | **body 끝** |

→ 1차 제출본의 생 `<script>`(≈235,745 위치)는 실제로 JS 번들보다 **먼저** 실행됐다. 개발 주석은 JS 에 한해 사실이었다.
증거 보강: `moa/js/product/detail.js` 1행이 `document.getElementById('sample-name')` 를 **널 체크 없이** 참조한다.
`#sample-name` 은 `product/detail.html` 꼬리에 있으므로, 이 파일이 head 에서 돌았다면 라이브가 즉시 죽는다.

**R5 의 본 사유는 유효하다** — `/ds/css/detail.css` 404 실측(현재도 404), 스킨 스코프 미보장, body 중간 렌더블로킹 스타일시트.
F-6 이 그 셋을 모두 해소했고, 덤으로 JS 실행 순서를 `@js` 순서로 **명시적으로 보장**하게 됐다(§3 R5).

> 이 두 건은 내 근거 수집이 얕았던 것이고, 개발이 실측으로 잡아낸 것이 맞다. 기록으로 남긴다.

## 2. P0 — 아직 안 고쳐진 것 (REJECT 사유)

### P0-1. 【R2 미해소】 하단바가 **노치 기기에서 푸터 마지막 줄을 25.9px 가린다** — K-12 AC3

**측정 결과 (Chromium 390×844, 최하단 스크롤):**

| safe-area-inset-bottom | 바 높이 | 푸터 padding-b | 푸터 margin-b | 푸터 마지막 내용 하단 | 바 상단 | **여유** |
|---|---|---|---|---|---|---|
| **0px** (비노치) | 92px | 100px | 0px | y=743.9 | y=752 | **+8.1px ✅** |
| **34px** (아이폰 노치) | **126px** | 100px | 16px | y=743.9 | y=718 | **−25.9px ❌** |

가려지는 요소: `DIV.footer__bottom`(사업자정보·저작권 줄).

**원인 2가지 — 둘 다 실측으로 확정:**

**(a) `margin-bottom` 은 스크롤 영역을 늘리지 못한다.**

```
safe=0  → document.scrollHeight = 5364,  .footer margin-bottom = 0px
safe=34 → document.scrollHeight = 5364,  .footer margin-bottom = 16px   ← 그대로다
```

CSS 스크롤 가능 영역(scrollable overflow)은 자손의 **보더박스**로만 정해진다.
마지막 블록의 **바깥 여백은 포함되지 않는다.** 즉 개발이 얹은 16px 은 **0px 만큼 일한다.**
`ds/css/detail.css:88` 의 규칙은 문법도 값도 맞지만, **고르는 속성이 틀렸다.**

**(b) 바 높이가 82px 이 아니라 92px 이다** (아래 P0-2). 부족분 상수 `18px` 이 그 잘못된 82 에서 나왔다.

**대안 3안을 실제로 렌더해 비교했다 (safe=34):**

| 안 | scrollHeight | 여유 | 판정 |
|---|---|---|---|
| 현재: `html body .footer{margin-bottom:max(0,sa−18)}` | 5364 | **−25.9px** | ❌ |
| `.footer{padding-bottom:calc(100px + sa)}` (important 없이) | 5364 | −25.9px | ❌ 스킨 `!important` 에 짐 |
| `#wrap{padding-bottom:…}` | 5390 | −25.9px | ❌ 푸터가 `#wrap` 밖이다 |
| **`html body{padding-bottom:max(0px, calc(env(safe-area-inset-bottom) − 8px))}`** | **5406** | **+16.1px** | ✅ |

**수정 지시**
```css
@media (max-width: 1023px) {
  /* .footer 의 padding 은 important 로 잠겨 있고, .footer 의 margin 은 스크롤 영역을
     늘리지 못한다(실측: scrollHeight 불변). 스크롤 컨테이너 쪽 padding 으로 확보한다. */
  html body { padding-bottom: max(0px, calc(env(safe-area-inset-bottom) - 8px)); }
}
```
- 상수 `8px` = **실측 바 높이 92px − 스킨 예약 100px**. P0-2 로 바를 83px 로 줄이면 `17px` 로 바꾼다.
- `.footer` 의 `margin-bottom` 규칙은 **삭제**한다(무효 코드).
- 새 `!important` 0개. 비노치 기기에서는 `max()` 가 0 을 골라 **현재와 완전히 동일**하다.

### P0-2. 【신규】 하단바 실측 높이가 **92px** 이다 — K-12 AC2 (명세 82px)

`ds/css/detail.css:981` 의 `gap: 9px` 은 `flex-wrap:wrap` 컨테이너에서 **row-gap 으로도** 작동한다.
금액줄과 버튼줄 사이에 9px 이 들어가고, 여기에 `border-top: 1px` 이 더해진다.

```
실측 (safe=0):  바 top=752  bottom=844  →  92px
   내역: border-top 1  +  .zg-bar__sum 28  +  row-gap 9  +  버튼 54  =  92
검증: row-gap:0 을 주면 → 바 높이 117px(safe=34) / 83px(safe=0)  ← 9px 이 사라진다
```

개발 보고 *"금액줄 height:28px(패딩 0) + 버튼 54px = 82px"* 는 **row-gap 9px 과 border 1px 을 빠뜨렸다.**
이 오차가 그대로 P0-1 의 상수 `18px` 로 흘러들었다.

**수정 지시**: `@media(max-width:1023px)` 의 `.zg-detail .mobile-fix-footer` 에
`gap: 9px` → `column-gap: 9px; row-gap: 0;` (버튼 사이 간격은 유지, 줄 간격만 제거) → 83px.
그리고 P0-1 의 상수를 `17px` 로 맞춘다. 82px 로 정확히 맞추려면 `border-top` 을 `box-shadow: 0 -1px 0` 로 바꾸면 된다(선택).

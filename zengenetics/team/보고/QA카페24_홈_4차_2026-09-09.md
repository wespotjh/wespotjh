# 1. 재배포 절차 — 「③④ 2개뿐」 검증

## ① 2개만 덮어써도 되는가 — **된다**

- `index.html`(불변)의 선언은 `<!--@css(/ds/css/home.css)-->` 21행 · `<!--@js(/ds/js/home-blocks.js)-->` **22행** · `<!--@js(/ds/js/home-hero.js)-->` **23행**. **파일명·경로·선언 순서 모두 그대로**다. 4차는 두 파일의 **내용만** 바뀐다.
- 그래서 번들 레코드 목록도 그대로다(§2). 이름이 바뀌었다면 `index.html` 도 같이 올려야 했다 — 그런 변경 없음.
- 방법은 **[화면 추가]가 아니라 기존 파일 전체 교체**다. (3차 때 새로 만든 파일이므로 이미 존재한다. [화면 추가]를 다시 누르면 이름 충돌·중복 파일 사고가 난다.) 배포표에 그렇게 명시했다.

## ② 중간 상태(하나만 저장)에서 홈이 깨지는가 — **깨지지 않는다**

- 두 파일이 공유하는 것은 `window.ZG_HOME` 네임스페이스뿐이고(`blocks:25` 생성 · `hero:23` 참조, `hero:25-26` 이 없을 때를 대비한 폴백까지 있다), **4차는 그 인터페이스를 건드리지 않았다** — 추가된 것은 `blocks` 내부의 `prepare()`·`ready()`, `hero` 내부의 `onStage` 뿐이다.
- 따라서 네 조합이 전부 성립한다: (3차,3차)=지금 상태 · **(4차 blocks, 3차 hero)** = 번쩍임만 먼저 해결 · **(3차 blocks, 4차 hero)** = 버벅임만 먼저 해결 · (4차,4차)=목표.
- 순서 지정 불필요. 배포표에 "순서 상관없음, 다만 둘 다 저장해야 온전하다"로 적었다.

# 3. `data-zg-fr` 속성 생존

- `index.html`·`home.css` 어디에도 `data-zg-fr` 문자열이 **없다**(grep 0). `home-blocks.js` 가 런타임에 `b.plate.setAttribute('data-zg-fr', …)` 로만 붙인다(135·140행).

# 5. ⑥ 「잠깐 멈춤」 문구 — 부적절. 수치로 특정해 다시 썼다 + 개발 권고(P1)

## 무엇을 쟀나

`home-blocks.js` 4차의 게이트: 블록이 3화면 앞에 오면 `prepare()` → 프레임 24장에 `im.decode().then(fin,fin)` → **24장 전부 끝나야 `ready`** , 아니면 **8,000 ms 뒤 `late`** 로 강제 개방. 개방 전에는 1번 컷 고정.

| 측정 (Chromium 153 headless · 390×844 · iPhone UA · 로컬 서버 · 실제 86장 사용) | 3차 | 4차 |
|---|--:|--:|
| 히어로를 지나 가루 블록에 머무는 동안 **three.js 렌더 호출** | **약 24회/초** (11초 동안 +268회) | **0회** (호출 수 1,559에서 정지) |
| 스크럽 중 빈 판(`complete && naturalWidth>0` 실패) | 0 | **0** |
| 게이트 개방 시각 | — | **`wait` → 8,000 ms 후 `late`** (`ready` 도달 실패) |
| 그때 프레임 24장의 실제 적재 상태 | — | **24/24 이미 완료** (첫 스냅샷부터) |

**히어로 렌더 정지는 주장 그대로 작동한다** — 이것이 「버벅임」의 원인 제거다(개발 §1-3 귀속과 일치).

## ★ 그런데 게이트가 `ready` 에 도달하지 못한다 (P1 권고)

원인을 분리하려고 같은 이미지 24장만 담은 **맨 페이지**로 재현했다(스택 배치·`opacity:0`·`loading=lazy` 동일):

```
{"done":7, "rej":0, "loaded":24, "firstMs":49, "lastMs":97, "elapsed":9001}
```

- **24장 전부 내려받기는 끝났는데(`loaded:24`), `decode()` 는 7개만 확정되고 17개는 9초가 지나도 pending** 이었다. 확정된 것들은 49~97 ms 로 즉시 끝났다.
- 즉 **화면에 실제로 그려지지 않는(겹쳐 쌓인 `opacity:0`) 이미지의 `decode()` 는 브라우저가 미룬다.** 그래서 이 게이트는 **거의 항상 8초 만료로 열린다** — 개발이 의도한 "다 받으면 곧바로"가 아니라 **"8초 뒤"** 가 표준 경로가 된다.
- 개방 뒤에는 정상이다(낱장 검사 `ready(nx)` 가 이미 통과 상태, 빈 판 0, 프레임 교체 정상).
- **대표님 체감:** 블록이 3화면 앞에 왔을 때 타이머가 시작되므로 **실제로 보이는 정지 시간 = 8초 − (3화면 전부터 도달까지 걸린 시간)**. 천천히 내려오면 짧고, 곧장 내려가면 **최대 8초 가까이** 1번 컷이 멈춰 있다. 「잠깐」이 아니다.

**권고(개발 판단 사항, 이번 판 반려 사유 아님):** 게이트 조건을 `decode()` 전량 대신 **`complete && naturalWidth > 0` 전량**(또는 앞 6~8장만)으로 바꾸면 같은 보호를 유지하면서 개방이 1초 이내로 내려간다 — 빈 판을 실제로 막는 것은 교체 직전의 낱장 검사 `ready(nx)` 이고, `decode()` 는 그 위의 선택적 최적화일 뿐이다. `decode()` 는 결과를 기다리지 않고 쏘아 두기만 해도 된다.
(내 측정은 headless Chromium + SwiftShader 다. 실기 iOS Safari 에서 `decode()` 가 곧바로 확정될 가능성은 남아 있다 → **실기 항목**. 다만 그 경우에도 8초 상한은 코드상 확정이므로 대표님 안내 문구는 8초 기준으로 써야 한다.)

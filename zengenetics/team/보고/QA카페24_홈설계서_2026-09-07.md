## b-2. **업로드 위치 — 설계서 판정을 뒤집는다**

### 문제: `ds/image/home/{bg,tex,stick,diss}/` = **새 폴더 5개**

실측: 저장소·라이브 모두 **`ds/image/` 에 하위 폴더가 하나도 없다**(`ico_price1.png`·`ico_price2.webp` 2개뿐).
`/ds/image/home/` → 404. 즉 설계대로 하면 대표님이 편집기에서 **폴더를 5개 새로 만들어야 한다.**

> **이것이 정확히 `ga4.js` 사고의 조건이다.** 대표님이 「화면 추가」 대신 「폴더 추가」를 눌러 `ga4.js` 라는
> **지울 수 없는 폴더**가 생겼고, 그래서 파일명을 `zg-ga4.js` 로 우회했다. 그 사고는 폴더 **1개**에서 났다.
> 이 설계는 **5개**를 만들라고 한다. 그중 4개는 한 단계 더 깊다.

## b-4. ★ **R3(적용 전 검증 불가)를 없애는 길 — 설계서가 놓쳤다**

설계서 R3: *"미적용 디자인의 정적 파일은 404 → 이미지 86개를 적용 전에 검증할 수 없다."* **맞다.** 다만 **스킨에 올릴 때만 그렇다.**

**이 몰은 이미 스킨 밖 이미지 경로를 쓰고 있다.** 상세설명 이미지가 그것이다:

```
/web/upload/NNEditor/20260826/mobile/fdb371740741f4f14073952ca3c1562b_1787719442.png
  → 200 · image/png · 165,478 B      ← 적용 스킨과 무관하게 서빙된다
/web/upload/NNEditor/20260826/00_….png
  → 200 · image/png · 344,390 B
```

칼륨 상품 하나에만 이 경로로 **14~27장**이 이미 올라가 있다. **대량 업로드 전례가 이 몰에 실제로 있다.**

`/web/upload/` 로 두면:
- **폴더 문제 소멸** (스킨 편집기를 안 쓴다)
- **R3 소멸** — 적용 전에 86장을 전부 `curl` 로 200 확인할 수 있다. **홈에서 가장 무서운 위험이 사라진다**
- 스킨을 되돌려도 이미지는 남는다(R11 완화)
- 대가: 스킨과 버전이 분리된다. 홈 이미지는 어차피 홈 전용이라 실질 손해가 작다

**미확인 1건:** `/web/upload/` 에서 **WebP** 가 `image/webp` 로 나오는지는 확인 못 했다(현재 그 경로에 WebP 가 없다).
→ **코드 착수 전 「WebP 1장 시험 업로드 → `curl` 로 200 + `image/webp` 확인」. 30초면 끝난다.**
`nosniff` 때문에 이게 틀리면 81장이 전부 안 뜬다. **이 한 번의 시험이 86장의 운명을 결정한다.**

## b-5. 72장 감축 — **설계서의 스프라이트 비권장 판단은 옳다. 그리고 감축할 필요가 없다**

설계서 C-2(스프라이트) 비권장 근거 *"2,240×4,482 = 10.04 Mpx → 디코드 시 RGBA 40 MB"* 는 **산수가 맞다**
(2240×4482×4 = 40.2 MB). iOS Safari 의 단일 이미지 디코드 한계(기기별 상이, 저사양에서 수백 Mpx 누적 시 강제 해제)를 고려하면
**한 장에 40 MB 를 올리는 것보다 72장을 나누는 편이 안전하다.** 게다가 스프라이트는 **프레임별 지연로딩을 없앤다** —
72장 중 화면에 필요한 몇 장만 받던 것이 **항상 전량 다운로드**가 된다. 총 바이트가 줄지도 않는다.

**추가로: 72장은 이미 잘 압축돼 있다.** 530,984 / 72 = **평균 7,375 B/장**(560×747). 더 줄일 여지가 크지 않다.
**감축의 진짜 이유는 용량이 아니라 "업로드 86회"였고, §b-4 가 그 이유를 없앤다.**

→ **C-1(86장 유지) 채택에 동의한다.** C-3(24→12프레임)은 디자인 변경이므로 개발·QA 가 결정할 사안이 아니라는 설계서 판단도 옳다.
설계서가 `frameEl(i)` 함수 1개로 프레임 접근을 격리해 두겠다고 한 것은 **좋은 보험**이다. 유지하라.

# (c) `position:sticky` 386vh — **성립한다. 그러나 "파괴 요소 0건" 은 사실이 아니다**

## c-1. 기본 상태에서는 성립한다 ✅

홈 전용 CSS 번들 **2벌 232,159 B 전문**을 파싱해 `html`·`body`·`#wrap`·`#container`·`#contents`·`main`
**자체에 걸린 규칙만** 추출했다(자손 선택자 제외). 무조건 적용되는 것 중
`overflow`·`transform`·`filter`·`backdrop-filter`·`contain`·`perspective`·`will-change`·`content-visibility` 는 **0건**이다.

```
main#contents { max-width:100%; padding:0; }          ← 풀블리드 (설계서 §2-1 정확)
html          { margin:0; padding:0; width:100%; height:100%; }
body          { margin:0; padding:0; font-…; position:relative; left:0; transition:left 500ms; }
#contents     { position:relative; padding-bottom:100px; }
#wrap.m-fixed { padding-top:40px; }
```
`body{position:relative}` 는 sticky 를 깨지 않는다. **기본 상태 판정: 돈다** ✅

## c-2. ★ **그러나 상태 클래스 3건이 sticky 를 죽인다 — 설계서 누락**

| 규칙 | 붙이는 주체 | 홈에서 실제로 일어나는가 |
|---|---|---|
| **`body.eMobilePopup{ overflow:hidden; position:fixed; }`** | 시스템 번들 **`addClass('eMobilePopup')` 3곳** — ① **모바일 검색 자동완성**(헤더 검색창에 글자를 치는 순간) ② **배너 팝업 풀사이즈 열기**(`BANNER_POPUP_OPEN`) | **일어난다.** 홈 라이브에 `.mpopup` **16회** · `df-banner-code` **13개** · 헤더 검색 존재 |
| `html.scroll-disabled{ overflow:hidden !important; }` | 사용자 번들 `rv_lt.js`(알파리뷰 팝업) | 홈에 `rv_frame.html` 유지 예정 → 일어난다 |
| `body.expand{ overflow-x:hidden; }` | 설정 주체 미확인(`addClass('expand')` 리터럴 0건) | 미확인 |

**`position:fixed` 가 `body` 에 붙으면** 문서가 흐름에서 떨어져 나가면서 **화면이 문서 최상단으로 튀고, `sticky` 는 전부 죽는다.**
상세 페이지에서는 눈에 잘 안 띈다. **386vh 히어로 위에서는 치명적이다** —
스크롤 60 % 지점에서 검색창을 탭하면 히어로가 처음으로 되감긴다.

**그리고 더 나쁜 것:** 시스템 번들 전문에서 **`removeClass('eMobilePopup')` 리터럴이 0건**이다.
붙이는 코드만 3곳 있고 떼는 코드가 문자열로 존재하지 않는다.
(변수·동적 문자열로 지울 가능성은 남아 있어 **단정하지 않는다** → 실기 확인 항목.)
**한 번 붙고 안 떨어지면 홈은 스크롤 자체가 멈춘다.**

### 그래서 요구한다 — 설계서 §6 에 **조건 ④** 를 신설하라

> **조건 ④. 상태 클래스에 의한 sticky 정지에 대비한다.**
> - `body.eMobilePopup` · `html.scroll-disabled` 를 `MutationObserver(attributes:['class'])` 로 감시한다.
> - 붙는 순간: 현재 `scrollY` 를 저장하고 히어로 렌더를 **동결**(rAF 중단).
> - 떨어지는 순간: `scrollY` 복원 + `lastP=-1` 강제 재계산 후 렌더 재개.
> - 스킨 코드는 수정 금지 파일이므로 **우리 쪽에서만 흡수한다**(§6-2 의 40px 대응과 동일 원칙).
> - **미리보기 실기 필수 항목:** ① 히어로 중간에서 헤더 검색창 탭 → 닫기 → 히어로가 원위치로 돌아오는가
>   ② 팝업 열기 → 닫기 → 스크롤이 되는가

## c-3. 나머지 조건 3개 — 설계서 판단이 맞다

| 조건 | 재검증 |
|:--:|---|
| ① `#wrap.m-fixed` 40px | **정확하다.** `scrollHeaderFixed()` 원문 복원: `mCutLine = $('.top-banner').length>0 ? $('.top-banner').outerHeight() : 0` → `getScroll > mCutLine` 에서 `$('#wrap').addClass('m-fixed')`. **홈에 `.top-banner` 가 실재**(라이브 5회)하므로 mCutLine>0, 즉 **상단띠를 지나는 순간** 40px 이 붙는다. 진행률 무캐시 재계산 + `lastP=-1` 대응 **충분하다**(§(e)-2 에 보강 1건) |

## 내 판정

- **`node --check` 통과** · `detail.css` 는 md5 불변(`f8095b8b`)인데 **칩 CSS(`.zg-opt__tag`·`.zg-opt__add`·`.zg-opt__mt > em`)는 이미 N개를 받도록 돼 있어 깨지지 않는다.** `zg-bar--soldout` 과 인라인 `display` 도 충돌하지 않는다(`''` 는 인라인 속성 제거라 클래스 규칙이 산다).

3. **운영 규칙 3번(착수 후 동결)이 세 번 연속 깨졌다.** 팀장 §3-1 이 지적한 「게이트가 이전 판에 PASS 를 찍는」
   구멍이 지금 실시간으로 재발하고 있다. **규칙에 강제력이 없으면 규칙이 아니다** —
   해시가 바뀌면 그 파일을 대상으로 하는 게이트 판정을 **자동 무효**로 두는 절차가 필요하다.

**칼륨 배포는 이 파일의 재판정 전까지 보류해야 한다.** 홈 설계 승인과는 무관한 별건이다.

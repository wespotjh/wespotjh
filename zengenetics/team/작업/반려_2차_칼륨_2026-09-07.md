## ★ 검수 방법 개선 — 팀 전체 적용
신아린이 2차부터 **Chromium(Playwright, SwiftShader)** 으로 실제 렌더해 픽셀로 측정했다.
Playwright 는 **zengenetics.co.kr 접속만 차단**돼 있고, `curl` 로 받아 로컬에 저장한 HTML 을
여는 것은 **된다.** 스킨 CSS 27개를 실제 번들 순서대로(`@layout`→`@import`→`@css` 재귀) 인라인하고
`optimizer.php` 원문의 런타임 행 마크업을 주입하면 **레이아웃을 실제로 계산할 수 있다.**
→ **jsdom 으로 "레이아웃은 못 잰다"고 넘기지 마라.** 이 방법으로 1차 실기 잔여 6건 중 3건이 코드로 확정됐다.

## 신아린의 1차 근거 정정 2건 (기록)
- **정정 1**: `.footer{padding-bottom:100px !important}` 가 `css/module/product/detail.css:4248`(≤1023px)에 **실재한다.**
  1차에 1행의 60px 만 인용한 것은 불완전했다. **개발이 옳았다.** 단 결론(가림)은 유효하다.
- **정정 2**: `optimizer_user.php` 는 **CSS 번들이 head, JS 번들은 `</body>` 근처**(289,446 / 291,346 byte)다.
  1차 개발 주석 "번들보다 뒤에 파싱"은 **JS 에 한해 사실이었다.** 문가온도 독립적으로 같은 오프셋을 얻었다.
  보강 증거: `moa/js/product/detail.js` 1행이 `#sample-name` 을 널 체크 없이 참조 — head 에서 돌면 라이브가 즉시 죽는다.

## 고칠 것 — P0 2건 (둘 다 K-12 하단 고정바)

### G-1. 하단바가 노치 기기에서 푸터 마지막 줄을 25.9px 가린다 (K-12 AC3)
`ds/css/detail.css:88`

| safe-area | 바 높이 | 푸터 padding-b | margin-b | 여유 |
|---|---|---|---|---|
| 0px | 92px | 100px | 0px | +8.1px ✅ |
| **34px(노치)** | **126px** | 100px | 16px | **−25.9px ❌** `DIV.footer__bottom` 가림 |

**원인 (a) — `margin-bottom` 은 스크롤 영역을 늘리지 못한다.**
실측 `document.scrollHeight` 가 safe=0 / safe=34 **양쪽 다 5364 로 동일**했다.
스크롤 가능 영역은 자손의 **보더박스**로만 정해지고 마지막 블록의 **바깥 여백은 포함되지 않는다.**
`detail.css:88` 은 문법·값은 맞지만 **고르는 속성이 틀렸다.**
**원인 (b)** — 바 높이가 82 가 아니라 92px (G-2).

**수정**: 신아린이 3안을 실제로 렌더해 비교한 결과 아래 1안만 통과했다(scrollHeight 5406, 여유 +16.1px,
새 `!important` 0, 비노치에서는 현재와 완전히 동일).
```css
html body { padding-bottom: max(0px, calc(env(safe-area-inset-bottom) - 8px)); }
```
- `.footer{padding-bottom}` → `!important` 에 짐. 채택 불가.
- `#wrap` → 푸터가 그 밖에 있음. 채택 불가.
- **상수 `8px` 은 G-2 를 고친 뒤 재측정해서 확정하라.** 지금 값은 92px 전제다.

### G-2. 하단바 실측 높이가 92px 다 (명세 82px, K-12 AC2)
`gap:9px` 이 `flex-wrap` 컨테이너에서 **row-gap 으로도** 작동한다.
`border-top 1 + 금액줄 28 + row-gap 9 + 버튼 54 = 92`. `row-gap:0` 을 주면 92→83 확인됨.
**이 오차가 그대로 G-1 의 상수 `18px` 로 흘러갔다.**
**수정**: `row-gap` 을 명시적으로 0 으로 두거나 레이아웃을 바꿔 82px 에 맞춘다. 고친 뒤 G-1 상수를 재측정한다.

## 고칠 것 — P1 2건

### G-3. 삭제 컨트롤이 12×12px 다
기획 §6-3 규칙 6 이 카드 삭제를 막았으므로 이것이 **유일한 취소 경로**인데,

`loading="lazy"` 가 무력화될 수 있다 — 로드 전 높이가 0 이라 브라우저가 14장을 전부
"화면 안"으로 판정해 **동시 로드**할 수 있다. 모바일 LCP 직격이다.
**F-1(SEO 색인)과 성능의 맞교환이므로 임의 판단 금지.**
→ **팀장 조정 결과(아래 §조정 1)를 따르라.**

## 팀장 조정 사항

### 조정 1 — G-4 는 "색인을 지키면서 성능도 지킨다"로 간다
F-1 을 되돌리지 않는다(색인 소실은 P0 였다). 대신 **로드 전에도 자리를 차지하게** 만든다.
- `#prdDetail img` 에 **로드 전 최소 높이**를 CSS 로 준다(예: `min-height` 또는 `aspect-ratio`).
  상세 이미지는 폭이 전부 1080px 로 동일하고 높이만 다르므로, 개별 높이를 몰라도
  **폭 기준 최소 높이 하나**로 "높이 0" 상태만 없애면 `loading="lazy"` 가 정상 동작한다.
- 첫 1~2장은 `loading="eager"`, 나머지는 `lazy` 를 유지한다.
- 고친 뒤 **신아린이 실제 렌더로 동시 로드 개수를 세어** 확인한다. 숫자로 증명하지 못하면 미해소다.

### 조정 2 — K-04 AC11 은 문서를 코드에 맞춘다 (개발 잘못 아님)
기획 AC 는 `role="button"` + `aria-pressed` 인데, 문가온의 접근성 P1 지시로
`data-zg-on` + `aria-label` 로 대체됐다. **문가온의 지시가 옳다** — `aria-pressed` 는
"다시 누르면 해제"를 약속하는데 실제로는 해제되지 않아 스크린리더가 거짓 정보를 준다.
→ **기획 문서 `01_기획_칼륨변환.md` 의 K-04 AC11 을 현재 코드에 맞게 개정한다.**
   개발은 코드를 되돌리지 마라. 신아린은 이 건을 오구현에서 뺀다.

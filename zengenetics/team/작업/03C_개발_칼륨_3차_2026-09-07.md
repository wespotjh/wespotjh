### 3-4. G-1 — 상수를 없앤 근거

지시서는 `8px`(바 92px 전제)을 주면서 **"G-2 를 고친 뒤 재측정해서 확정하라"** 고 했다. 재측정 결과:

| 후보 | 여유 @safe=0 | 여유 @safe=34 | 판정 |
|---|---|---|---|
| `max(0px, calc(sa − 18px))` (82px 전제로 환산한 값) | +17.9px | **0.0px** (딱 붙음) | 위험 — 반올림·안티에일리어싱에 잠식될 수 있다 |
| **`env(safe-area-inset-bottom)`** | **+17.9px** | **+17.9px** | ✅ 채택 |

산수로도 상수가 필요 없다:
```
바 높이 = 82 + sa          (G-2 확정)
예약    = 100(스킨 !important) + P
여유    = 100 + P − (82 + sa) = 18 + P − sa
→ P = sa 로 두면 여유 = 18px (sa 와 무관하게 일정)
```
```css
@media (max-width: 1023px) { html body { padding-bottom: env(safe-area-inset-bottom); } }
```
- `max()`/`calc()` 도 필요 없어져 **iOS 11.3+ `env()` 만으로 동작**한다(2차 안보다 호환 범위가 넓다).
- 비노치에서는 `env()` 가 0 → **현재와 완전히 동일**. 새 `!important` **0개**.
- 2차의 `.footer{margin-bottom}` 규칙은 **삭제**했다(실측상 0px 만큼 일하는 무효 코드).

### 5-2. 진짜 원인 — `aspect-ratio` 만으로는 안 됐다

스크립트 실행 직후(로드 전) 상태를 찍어 보니:

| | `aspect-ratio` 만 넣었을 때 | **`min-width` 까지 넣은 뒤** |
|---|---|---|
| computed `aspect-ratio` | `auto 1080 / 1600` | `auto 1080 / 1600` |
| computed `width` | **0px** | **390px** |
| computed `height` | **0px** | **577.8px** |
| 14장의 `rect.top` | **전부 2965 (한 점에 겹침)** | 2965, 3543, 4121 … 10476 (**578px 간격**) |
| 스크립트 직후 요청 | **14** | **2** |

**원인:** 스킨 `.productDetail img{ width:auto !important }` 때문에 자연 치수가 없는 상태에서 폭이 **0px** 으로 계산된다.
폭이 0 이면 `aspect-ratio` 를 줘도 높이가 0 이라 14장이 한 점에 겹치고, 브라우저는 전부 "뷰포트 안"으로 판정한다.
폭은 `!important` 로 잠겨 있어 이길 수 없으므로 **잠기지 않은 `min-width`/`min-height` 로 최소 크기를 만들었다.**

```css
.zg-detail #prdDetail .zg-fold img { aspect-ratio: auto 1080 / 1600; }   /* auto = 로드 후 자연 비율 우선 → 왜곡 0 */
@media (max-width: 1023px) { .zg-detail #prdDetail .zg-fold img { min-width: 100%; } }
@media (min-width: 1024px) { .zg-detail #prdDetail .zg-fold img { min-height: 320px; } }
```
- **≤1023px 은 컨테이너가 항상 원본 1080px 보다 좁으므로 `min-width:100%` 가 확대를 일으키지 않는다.**
- ≥1024px 은 컨테이너가 1080px 보다 넓을 수 있어 **폭은 건드리지 않고** 최소 높이만 예약했다(모든 상세 이미지의 렌더 높이보다 낮은 값 → 왜곡 없음).
- `aspect-ratio` 의 **`auto` 키워드**가 핵심이다 — 로드 전에는 지정 비율, 로드 후에는 **자연 비율이 우선**이라 이미지가 늘어나지 않는다.

## 9. 이번 라운드에서 내가 가장 불안한 것

**G-4 의 `min-width: 100%` 가 ≤1023px 전 구간에서 확대를 일으키지 않는다는 전제.**
근거는 "상세 이미지 원본 폭이 1080px 이고 1023px 뷰포트가 그보다 좁다"인데,
이건 **11번 상품에서 실측한 값**이다. 8종 복제 때 어떤 상품의 NNEditor 이미지가 1023px 보다 좁게 올라오면
그 상품에서만 이미지가 늘어나 흐려진다(레이아웃은 안 깨진다).

- 지금 막을 수 있는 방법: `min-width: min(100%, 1080px)` 로 상한을 두는 것인데, 그러면
  **1080px 보다 좁은 원본이 1080px 까지 확대**돼 문제가 오히려 커진다. 그래서 채택하지 않았다.
- **8종 복제 전 확인 요청:** 각 상품 상세설명 이미지의 원본 폭이 전부 1080px 인지 관리자에서 확인해 주십시오.
  한 종이라도 다르면 그 상품만 `min-width` 를 빼거나 상품별 비율 토큰을 주는 방식으로 처리하겠다.
  (11번은 실측 완료 — 14장 전부 1080px, 브리프 §1-1 근거와 일치)

**두 번째로 불안한 것: R-2 의 61·62 런타임 결과.**
마크업 근거(정적행이 `<tbody class="">` 로 노출 · `quantity_opt[] value="1"`)는 라이브 원문으로 확정했고
안내문이 사라지는 것도 그 마크업으로 재현했다. 그러나 **카페24가 그 정적행으로 `#totalPrice` 를 실제로 채우는지**는
런타임이라 확인하지 못했다(오세진 §(g)7 과 같은 항목). 채우지 않으면 61·62 는 "0원 + 안내문 없음"이 되는데,
이건 지금(안내문이 계속 떠 있음)보다는 낫지만 이상적이지도 않다. **61번 미리보기에서 하단바 금액만 봐 주시면 30초에 판정된다.**

부수적으로, 하네스에서 `document.scrollWidth 425 > clientWidth 390` 인 가로 넘침이 **모든 조건(우리 CSS 유무 무관)에서 동일하게** 관측된다.
외부 스크립트를 차단한 하네스 특성으로 보이나 **원인을 특정하지 못했다.** 실기에서 가로 스크롤이 생기는지 확인 요청드린다.

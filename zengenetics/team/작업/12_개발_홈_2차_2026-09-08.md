# 1. 1차 보고의 틀린 문장 2개 — 인정하고 철회한다

## C-1 「`pageerror` 0건」 — **사실이 아니었다**

라이브 홈 본문만 교체한 오세진 픽스처에서 `main_js.html` 이 **`TypeError: Cannot read properties of undefined (reading 'pause')`** 를 냈다.
**변경 전 기준선에는 없고 변경 후에만 난다 — 이번 변경이 만든 오류다.**

**내가 못 본 이유:** 내 픽스처는 카페24 시스템 JS 번들(`optimizer.php` — jQuery·Swiper 포함)을 **서빙하지 않았다**(로컬 서버에서 404).
그 상태에서는 `main_js.html` 이 Swiper 를 만들지 못해 `.autoplay.pause()` 에 **도달조차 하지 않았고**, 그래서 오류가 안 났다.
**"오류가 안 났다"가 아니라 "오류가 날 코드를 실행하지 않았다"였다.** 픽스처의 충실도 문제를 "0건"이라고 보고했다.
→ §3 에서 고쳤고, **번들을 실제로 싣는 하네스(§5)로 재현·해소를 둘 다 증명**했다.

## C-3 「우리 JS 가 `main_js.html` 보다 먼저」 — **거꾸로였다**

사용자 JS 번들은 `<head>` 가 아니라 **`</body>` 직전**(라이브 오프셋 269,775)이고, `main_js.html` 인라인은 본문 안(174,284)이다.
**`main_js.html` 이 먼저, 우리가 나중이다.** 칼륨 1차에서 확정된 사실을 잊고 썼다.

**결과에 영향은 없다** — M-1(상태를 `.zg-home` 에)·M-2(`window.onload` 미사용)는 실행 순서와 무관하게 성립하고, 1차 QA 가 `body` 클래스 제거 후 `.zg-home` 유지를 실증했다.

두 변수에 접근하는 멤버 전수(원문 grep): `.autoplay.pause` ×2 · `.destroy` ×1 · 난독화 `[autoplay]['start']`·`[slideNext]` ×2(**YouTube 배너 iframe 콜백 안 — 배너가 없어 도달 불가**).

### 선택 — 객체 스텁, DOM 스텁은 기각

두 가드가 **`== undefined`** 다. 변수를 미리 **정의해 두면 가드가 닫혀 `new Swiper` 자체를 건너뛴다** — 오류의 원인 문장이 실행되지 않는다.
`var` 재선언은 이미 있는 전역 값을 지우지 않으므로, **`main_js.html` 보다 먼저 실행되는 자리**(= `index.html` 인라인 `<script>`, §1 C-3)에 놓는다.

```js
window.runMainBannerSlidePC     = { autoplay: { pause: function () {} }, destroy: function () {} };
window.runMainBannerSlideMobile = { autoplay: { pause: function () {} }, destroy: function () {} };
```

- **도달 가능한 멤버만** — `autoplay.pause`(가드가 닫혀 실제로는 안 불림, 만약을 위해) · `destroy`(데스크톱 폭 `resize` 경로에서 **실제로 불린다**). YouTube 콜백의 `slideNext`/`start` 는 넣지 않았다 — 최소 원칙.
- **Swiper 를 흉내내지 않는다.** 빈 객체 + no-op 2개. 두 변수를 **서로 다른 객체**로 두어 한쪽 `destroy` 가 다른 쪽에 영향 없게 했다.
- **DOM 스텁(`<div class="jsMainSlidePC" hidden>…`)은 기각했다** — 그러면 Swiper 가 **실제로 생성**되고 `on:{init}` 콜백이 돌며, **그 콜백 안에 `$('body').removeAttr('class')` 가 있다**(R16). 오류 하나 지우려고 body 클래스 초기화를 다시 켜는 셈이다.

# 6. 개발이 가장 불안한 것 (2차)

**1) 스텁이 "이미 만들어졌다" 분기를 타게 한다는 것은, 그 스크립트가 배너 없이도 `destroy()` 를 부른다는 뜻이다.** 데스크톱 폭에서 `resize` 마다 no-op 이 불린다. 무해하지만 **모아스튜디오가 `main_js.html` 을 갱신하면 이 가드 조건이 바뀔 수 있다** — 그때는 H2 `err.pause` 가 다시 빨갛게 될 것이고, 그게 이 하네스의 존재 이유다.

**2) W-H1 승격 기준 `innerHeight×0.5` 는 내가 정한 숫자다.** "첫 화면 근처" 의 정의가 이것뿐인지 실기로 봐야 한다. 느린 망에서 사용자가 첫 화면에 머문 채 3D 가 켜지면 히어로가 100vh→386vh 로 늘어나는데, **스크롤 위치가 0 근처면 시프트가 아래쪽에서만 일어나** 화면은 안 튄다 — 하지만 SwiftShader 로 본 것이지 폰으로 본 것이 아니다.

**3) R17 이 하네스에서 실제로 잡혔다(§3-3-2).** 4 ms `setInterval` + 번들 부하로 rAF 가 굶는다. 실기에서 히어로가 뻑뻑하면 그 원인이다. 수정 금지 파일이라 우리가 못 고친다.

# 1. 무엇이 잘못이었나

4차 게이트는 **24장 `decode()` 가 전부 확정될 때까지** 스크럽을 시작하지 않았다.
그런데 겹쳐 쌓인 `opacity:0` 이미지의 디코드는 브라우저가 뒤로 미룬다 — 오세진 실측대로
**도착은 97ms 에 끝났는데 확정은 7/24 에서 멈춘다.** 그러면 8초 안전장치가 열 때까지 1번 컷이 고정된다.
손님 눈에는 "스크롤해도 가루가 안 움직인다" 로 보인다 — 반려하신 「버벅임」보다 나쁘다.

## 통제 재현 (내 환경에서도 그대로 났다)

내 스크럽 시나리오들(정상망·3g·9초 지연·접근 후 대기)에서는 `decode()` 가 100~230ms 안에 확정돼
**8초 만료가 재현되지 않았다.** 그래서 보고된 병리 자체를 조건으로 만들었다 —
`HTMLImageElement.prototype.decode` 를 **끝내 확정되지 않는 약속**으로 바꾸고 같은 시나리오를 돌렸다:

| 코드 | 게이트 `wait` | 게이트 열림 | 상태 | 그 시점 도착 프레임 |
|---|--:|--:|---|--:|
| **4차** (decode 게이트) | 3,973ms | **12,132ms (+8,159ms)** | **`late`** | 24 / 24 |
| **5차** (도착 게이트) | 3,572ms | **3,572ms (+0ms)** | **`ready`** | 24 / 24 |

오세진이 픽스처에서 본 것과 같은 모양(`wait → 8초 → late`)이 4차에서 재현되고, 5차에서 사라진다.

# 2. 고친 것 (`home-blocks.js` 1파일)

## 2-1. 게이트 조건 — `decode()` 전량 → **도착(`complete && naturalWidth>0`) 전량**

```js
var counted = false;
function fin() { if (counted) return; counted = true; if (++done >= n) open('ready'); }
if (im.decode) { im.decode().then(noop, noop); }   /* 내려받기 시작 + 되면 미리 디코드. 기다리지는 않는다 */
if (ready(im)) { fin(); return; }
im.addEventListener('load', fin);
im.addEventListener('error', fin);
```

- **왜 24장 전부이고 앞 6~8장이 아닌가** (지시 5): 게이트가 여는 조건은 이제 **도착**이고, 도착은 24장이
  같은 순간에 몰려 끝난다(오세진 실측 first 49ms · last 97ms — 폭 48ms). 앞 6장만 기다려도 이득이 48ms 뿐이라
  "몇 장을 기다릴지" 라는 새 상수를 만들 이유가 없다. 전량을 기다리는 편이 **중간에 스크럽이 멈칫할 여지가 없어** 더 안전하다.
  느린 회선이라 24장째가 정말 늦으면 그때는 8초 안전장치와 낱장 검사가 받는다.
- `decode()` 는 **호출은 유지**한다 — 지연로딩 중인 이미지의 내려받기를 시작시키고, 되면 미리 디코드해 준다.
  다만 그 **완료를 게이트 조건으로 쓰지 않는다**(성공/실패 모두 무시).
- `error` 도 `fin` 으로 센다 — 한 장이 404 여도 나머지가 멈추지 않는다. 그 장은 낱장 검사에서 걸러진다.
- **빈 판 방어는 그대로다** — 교체 직전 `ready(nx)` 낱장 검사가 막는다(§3 표 4·5행).
- **8초 안전장치는 남겼다** — 이제는 "도착 자체가 안 되는" 예외 경로다.

## 2-2. P2-i — `prepare()` 거리 상한 (문가온 권고, 판단 포함)

```js
var lead = vh * 3 < 4000 ? vh * 3 : 4000;
if (r.top < (lead > vh ? lead : vh)) prepare(b);
```

**권고의 전제는 실측에서 성립하지 않았다.** 트랙 높이가 `300vh` 라 **블록 간격도 뷰포트와 같이 커진다** —
`vh*3` 는 간격(`300vh`)의 1/100 이라 뷰포트가 아무리 커도 두 블록을 동시에 덮을 수 없다.
Googlebot 형태(411×9000, UA 포함)로 실측: 세 블록 모두 `data-zg-fr` 미설정(=`prepare()` 미실행),
diss 요청 30건은 눈에 보이는 히어로·트리오 몫이었다. **4차와 5차가 동일하다.**

그래도 **한 줄은 넣었다** — 이유는 셋이다. ① 상한이 붙어도 폰·태블릿·PC 에서 값이 바뀌지 않는다
(844 → 2,532 · 900 → 2,700 그대로). ② 뷰포트가 4,000px 을 넘으면 "화면에 들어왔을 때" 로 후퇴해
어떤 경우에도 최대 한 블록치(24장·192KB)만 붙잡는다. ③ 디자인이 가루 구간 레이아웃을 다시 짜고 있어
트랙 높이가 `vh` 비례가 아니게 되면 전제가 바뀌는데, 그때 이 상한이 유일한 방어선이 된다.
`lead > vh ? lead : vh` 로 쓴 이유: 단순히 4,000 으로 자르면 **뷰포트가 그보다 큰 경우 화면 안에 있는데도
준비를 시작하지 않는** 구멍이 생긴다.

# 6. 남는 유보

1. **`decode()` 무응답은 내가 주입해 만든 조건**이다. 오세진 픽스처에서 자연 발생한 이유(스크롤 없이 대기,
   소프트웨어 GPU, 스로틀 조합 중 무엇인지)는 특정하지 못했다. 다만 5차 게이트는 `decode()` 결과에
   **의존하지 않으므로** 그 이유와 무관하게 영향을 받지 않는다.
2. **첫 진입에서 아주 잠깐(≈0ms~수백ms) 1번 컷이 보이는 것은 그대로다** — 24장 도착까지의 시간이고,
   3화면 앞에서 미리 받으므로 보통은 도착이 먼저 끝난다. 아주 느린 회선에서 길어지면 8초 뒤 게이트가 열리고
   도착한 프레임만 순서대로 보인다(빈 판은 어떤 경우에도 안 켜진다).
3. 가루 구간 **레이아웃 재설계는 디자인 소관** — 손대지 않았다. 트랙 높이가 `vh` 비례를 벗어나면
   §2-2 의 4,000px 상한이 그때부터 실제로 일한다.

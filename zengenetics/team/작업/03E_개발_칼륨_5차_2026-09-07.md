## 2. H-1 — 상세 이미지 확대 (P0)

### 2-1. 내 전제가 틀렸다는 것을 먼저 독립 확인했다

지시받은 값을 그대로 쓰지 않고, **라이브 PNG 의 IHDR 청크를 직접 읽어** 재확인했다(Range 요청, 파일당 64바이트):

```
062142e1970af107766d287a36…png   IHDR  639 x 427
854172ca6164d54193146fc516…png   IHDR  640 x 1753
5d225a3ab2d2965287f949259c…png   IHDR  640 x 1671
54e6916dc3e1e618759ecddda9…png   IHDR  640 x 995
```

**모바일 경로가 실제로 받는 원본 폭은 639~640px 이다. 1080px 이 아니다.**

`640 × 948` 이 실측 중앙값이라는 것도 위 두 번째 파일에서 확인된다.

**동시 로드 억제·색인 승격·자리 분산 전부 유지된다.** H-1 수정이 G-4 를 되돌리지 않았다.

### 2-4. 적용 코드
```css
.zg-detail #prdDetail .zg-fold img { aspect-ratio: auto 640 / 948; }

@media (max-width: 1023px) {
  .zg-detail #prdDetail .zg-fold img { min-width: min(100%, 640px); }
}
@media (min-width: 1024px) {
  .zg-detail #prdDetail .zg-fold img { min-height: 320px; }
}
```
- `min(100%, 640px)` 은 **640px 보다 넓은 원본이 와도 확대하지 않는다** — 8종 전개 방향으로 안전하다.
- 640px 보다 좁은 원본이 오면 로드 전 예약 높이만 실제보다 커진다(**화질 영향 없음**).
- `aspect-ratio` 의 `auto` 키워드 때문에 **로드 후에는 자연 비율이 이겨** 어떤 원본에서도 왜곡이 없다.

## 3. H-2 — 클립한 `select` 의 가로 넘침 (P0)

### 3-1. 내 3차 결론이 틀렸다

3차 §9 에서 `scrollWidth 425 > clientWidth 390` 을 관측하고 *"우리 CSS 유무 무관"* 으로 적었다.
**내 하네스가 시트 ON/OFF 대조를 하지 않았기 때문**이고, 대조해 보니 반대였다.

| 조건 | `scrollWidth` | `clientWidth` | 넘침 | `select` 박스 | `display` / `visibility` |
|---|---|---|---|---|---|
| 수정 전(4차) | **425** | 390 | **+35px ❌** | 390px (right 425) | block / visible |
| **수정 후(5차)** | **390** | 390 | **없음 ✅** | **22px** (right 57) | **block / visible** |
| 우리 CSS OFF(대조) | 390 | 390 | 없음 | 268px (right 374) | inline-block / visible |

**원인:** `.zg-a11y-hide{width:1px}`(0,2,0)가 `…productOption select{width:100%}`(0,4,1)에 져서
**레이아웃 박스가 390px 그대로 남았다.** `clip-path: inset(50%)` 는 페인팅만 자르고 박스는 남긴다.

### 3-2. 적용 코드
```css
.zg-detail .xans-product-detail .infoArea .productOption select.zg-a11y-hide {
  width: 1px; height: 1px; min-width: 0;
}
```
(0,5,1) > (0,4,1) 이라 **로드 순서와 무관하게** 이긴다. 새 `!important` 0개.
`display`·`visibility` 는 건드리지 않았으므로 **카페24 옵션 검증의 포커스 경로가 그대로 유지된다**(K-04 AC1).
수정 후 `display:block / visibility:visible` 실측으로 확인했다.

## 7. 이번 라운드에서 배운 것 (같은 실수를 반복하지 않기 위해)

1. **"실측했다"고 쓸 때 무엇을 실측했는지 적어야 한다.** 나는 브리프의 "1080→860"을 인용하며 "11번 실측 완료"라고 썼는데,
   실제로 잰 것은 **프로토타입 webp** 였고 **라이브 모바일 원본(640px)** 이 아니었다. 이번엔 IHDR 을 직접 읽어 붙였다.
2. **"우리 CSS 무관"이라고 결론내려면 시트를 꺼 보고 대조해야 한다.** H-2 는 대조 한 번이면 3차에 잡혔다.
   하네스에 **ON/OFF 대조**를 기본으로 넣었다.
3. **전수 스캔은 대상 목록을 파일로 고정해야 한다.** `price.css` 를 빠뜨린 것은 목록을 매번 손으로 적었기 때문이다.
   §0 md5 표가 이제 그 목록 역할을 한다.

## 8. 가장 불안한 것

**`min(100%, 640px)` 의 `640` 이 다시 상수라는 점.**
이번엔 라이브 101장(신아린) + 내 독립 확인 6장으로 근거가 있지만, **관리자가 앞으로 올릴 이미지 폭은 보장되지 않는다.**
- 640px **보다 넓게** 올라오면: 확대는 없고(안전), 로드 전 예약만 실제보다 작아 스크롤 점프가 조금 커진다.
- 640px **보다 좁게** 올라오면: 예약이 커져 빈 공간이 잠깐 보인다. **화질 영향은 없다.**
→ 즉 **어느 쪽으로 틀려도 화질 회귀는 재발하지 않는다.** 다만 8종 전개 시 각 상품 첫 장의 IHDR 만
한 번 훑어 640 가정이 유지되는지 확인해 주시길 요청드린다(상품당 64바이트 Range 요청 1회).

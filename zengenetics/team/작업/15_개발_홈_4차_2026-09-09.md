## 1-3. 원인 귀속 — 트레이스가 지목한 곳은 **히어로 three.js** 였다

devtools 트레이스(같은 스크럽, 6배 스로틀)를 이벤트·스크립트별로 합산:

|---|--:|--:|---|
| `Commit`(합성기 커밋) | **3,666ms** | 168ms | 캔버스가 매 프레임 새 내용을 올리던 값 |
| `GPUTask` | 2,496ms | (상위 10 밖) | |
| `FunctionCall` 중 **`home-hero.js`** | **411ms** | 29ms | |
| `FunctionCall` 중 `home-blocks.js` | 216ms | 145ms | |

그 구간을 훑는 내내 WebGL 이 전체 화면을 다시 그려 메인 스레드와 합성기를 잡아먹었다.

## 1-4. 「빤짝」 — 조건을 만들자 재현됐다

일반 조건(로컬 즉시 응답·120ms 지연·400kbps)에서는 교체 23회 중 **준비 안 된 프레임 0회**였다 —
그래서 처음엔 재현되지 않았다. **프레임 이미지 도착을 9초 지연**시키자 결정적으로 나왔다:

| 조건 | 프레임 교체 | 준비 안 된 프레임을 켠 횟수 | 화면 |
|---|--:|--:|---|
| 3차 코드 · 이미지 9초 지연 | 23 | **20** (idx 3~22) | 빈 판이 프레임마다 번쩍 |
| 4차 코드 · 같은 조건 | **0** | **0** | 1번 프레임 고정(정지화면) |

원인은 오케스트레이터 가설 A 그대로다 — 24장이 같은 상자에 겹쳐 있어 레이아웃상 전부 뷰포트 안이라
`loading="lazy"` 가 늦게 한꺼번에 요청되고, **`.zg-on` 이 붙는 순간에 아직 디코드가 안 끝나 빈 판이 한 프레임 보인다.**
실기 LTE·첫 방문에서 이 조건이 실제로 만들어진다.

## 1-5. 기각한 가설

- **B(프레임이 띄엄띄엄)** — 교체는 매번 23~24장 전부 일어났고(`uniq` 23/24), 트랙 높이·장수는 프로토타입과 같다.
  느리게 보인 것은 **프레임 부족이 아니라 프레임 드롭**이었다. 그래서 크로스페이드·트랙 높이는 **건드리지 않았다**(연출 원안 유지).
- **C(`::after` 그라디언트 리페인트)** — `Paint` 총 168ms/5.8초. 병목 아님.
- `will-change` 는 애초에 금지 항목이고, 넣을 이유도 없었다.

# 2. 고친 것 (2파일 · 코드)

## 2-1. `home-hero.js` — 히어로가 화면 밖이면 그리지 않는다

```js
var onStage = true;
function onScroll() {
  var rect = track.getBoundingClientRect();
  onStage = rect.bottom > -80;          /* 히어로 트랙이 화면 위로 완전히 지나갔는가 */
  if (reduced || ZG.frozen) { if (reduced) pTarget = 0; return; }
  ...
}
...
function frame() {
  requestAnimationFrame(frame);
  if (ZG.frozen) return;
  if (!onStage) { pNow = pTarget; return; }   /* 그리지 않는다. 진행률은 목표값에 붙여 둔다 */
  ...
}
```

- rAF 루프 자체는 살려 둔다(복귀 시 즉시 재개, 리스너 추가 0).
- `pNow = pTarget` 로 붙여 두는 이유: 안 붙이면 되돌아왔을 때 lerp 가 옛 값에서부터 따라잡으며
  히어로 전체가 한 번 훑고 지나가는 연출이 보인다.
- `-80px` 여유는 iOS 주소창 높이 변화·바운스용.
- 접근성 축소모드(`reduced`)에서도 화면 밖이면 멈춘다 — `onStage` 계산을 `reduced` 검사보다 앞에 뒀다.

## 2-2. `home-blocks.js` — 디코드가 끝난 뒤에만 프레임을 켠다

```js

  각 img 에 대해 im.decode().then(fin, fin)  →  24장 모두 끝나면 'ready' + 스크럽 시작
  8초 안전장치: 그때까지 못 받으면 'late' 로 게이트를 열되, 낱장 검사가 빈 판을 계속 막는다 }

…

```

- `decode()` 는 지연로딩 중인 이미지의 **내려받기도 함께 시작**시킨다 → `loading="lazy"` 는 그대로 두었다.
  (전량 `eager` 로 바꾸면 72장이 첫 화면 로딩과 경쟁해 LCP 가 나빠진다 — SEO 게이트 기준.)
- **되돌릴 수 있게**(지시 3): 이미지가 끝내 안 오면 그 블록만 **1번 프레임 정지화면**으로 남고
  캡션·숫자 밴드·CTA 는 정상 동작한다. 상태는 `data-zg-fr="wait|ready|late"` 로 밖에서 볼 수 있다(클래스 아님).
- 메모리: 한 블록 24장(560×747) 만 3화면 앞에서 준비한다. 3블록을 다 지난 뒤 3번째 블록 실측 59.7fps —
  누적으로 나빠지는 징후 없음(§3).

# 7. 개발이 남기는 유보 (실기에서 확인해 주셔야 하는 것)

1. **헤드리스 Chromium ≠ 실기 GPU.** 6배 스로틀은 CPU 만 흉내 낸다. 실기에서 남는 버벅임이 있다면
   그것은 WebGL 렌더 자체(히어로 구간 안)의 문제이지, 이번에 고친 "화면 밖 렌더" 는 아니다.
2. **첫 진입에서 가루가 잠깐 멈춰 있을 수 있다** — 24장 디코드를 기다리는 시간이다(설계된 동작).
   3화면 앞에서 미리 받으므로 보통은 도착 전에 준비가 끝나지만, 아주 느린 회선에서는 정지화면이 길어질 수 있다.

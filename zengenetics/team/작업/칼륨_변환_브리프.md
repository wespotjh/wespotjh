# 🔴 브리프 §1-1 수치 정정 (2026-09-07, 오케스트레이터 자기정정)

**§1-1 에 적은 "라이브 1080px → 프로토타입 860px, 0.7963배" 는 CSS 상수의 근거로 쓰면 안 된다.**

내가 대조한 `dl_potassium_*.png` 14장은 **1080px 폭**이 맞았지만, 그건 **PC 경로**의 원본이다.
**라이브 모바일이 실제로 내려받는 것은 `/web/upload/NNEditor/20260826/mobile/*.png` 이고 폭이 639~640px 이다.**

내가 방금 라이브에서 다시 받아 PNG IHDR 을 직접 읽어 확인했다:
```
/web/upload/NNEditor/20260826/mobile/fdb37174…png  → IHDR (639, 592)   [200]
/web/upload/NNEditor/20260826/fdb37174…png         → 404 (PC 경로는 이 이름이 아니다)
기존 대조본 dl_potassium_01.png                     → IHDR (1080, 1000)
```
가로세로비는 셋 다 같다(592/639 = 0.9265, 1000/1080 = 0.9259) — **같은 이미지의 세 가지 크기**다.
따라서 **§1-1 의 결론(프로토타입 상세 = 라이브 상세, 교체 불필요)은 그대로 유효하다.**
틀린 것은 **폭 상수뿐**이다.

신아린이 3차에서 9종 상세 **101장 전수**의 IHDR 을 읽어 확정했다: **전부 {639, 640}. 1080px 은 한 장도 없다.**
(11 칼륨 14장 = 639px×5 + 640px×9 / 13·16·61·62·63 = 87장 전부 639~640)

**영향**: 개발이 G-4(로드 전 자리 예약)에서 `min-width:100%` 를 쓸 때 "원본 폭 1080px" 을 전제했고,
그 결과 **641~1023px 구간에서 상세 이미지가 최대 +55% 확대**됐다(768px→+20%, 900px→+36%, 1023px→+55%).
아이패드 세로(768/820/834)와 큰 폰 가로(932)가 전부 이 구간이다. **390px 에서는 드러나지 않는다.**

**앞으로**: 이미지 치수를 CSS 상수로 쓸 때는 **모바일이 실제로 받는 파일**의 IHDR 을 읽어라.
프로토타입 치수도, PC 경로 치수도 근거가 아니다.
